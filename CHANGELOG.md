# Changelog

All notable changes to this project are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

- Two focused skills, `review-code-security` and `review-code-accessibility` (`tools/skills_extra.py`, written to `skills/<name>/SKILL.md` by the build). Each reads the matching `concerns/<concern>.md` list, has a narrow description with a "do not use" clause, and is listed in the Agent Skills index, `agent.json`, and `ard.json`. `tools/eval.py triggers --focused` installs them beside the main skill to measure whether they take its queries.
- Pushing a tag such as `v0.1.0` runs `.github/workflows/release.yml`: it checks that the tag is on `main`, rebuilds, checks `skills/` is current, and publishes a GitHub release with generated notes.
- The home page leads with the promise and a sample verdict, prints the stable-card count from the build (141: 127 across the levels, 14 in the packs), and shows a last-updated date. The nav has six items. Level, pack, concerns, and guide pages have breadcrumbs, and `/guides` holds three explainers with Markdown twins.
- SEO and agent readiness pass (`docs/research/seo-audit-2026-11-02.md`). Titles and descriptions for results pages come from `tools/seo.py` (titles 40 to 62 characters, descriptions 110 to 160); every page gains `twitter:card`, a robots meta with large-snippet settings, `theme-color`, self-referencing `hreflang`, and JSON-LD (a page node plus a `BreadcrumbList`; the home graph adds keywords, `sameAs`, the repository, and the maintainer). New files: `agent.json` (endpoints, capabilities, authentication none; for `/?mode=agent` see `docs/deploy.md`), `/.well-known/ard.json` ([ARD](https://agenticresourcediscovery.org/spec/) v0.91, with `rel="ard"` and `Agentmap:`), and a real `/favicon.svg` and `/favicon.ico` in place of the inline icon. The page script registers read-only WebMCP tools (`start_review`, `list_levels`, `list_cards`). Headers gain `Permissions-Policy` and `Cross-Origin-Opener-Policy`. `AGENTS.md` now lists four binding specs.
- Filtered requests need the Worker less. The build also writes `cards/concern-<concern>.json`, `concerns/<concern>.md`, `concerns/level-<level>.md`, and a slim `cards-index.json` (`id`, `level`, `severity`, `concerns`, `topics`, `rule`, `url`; schema `cards-index.schema.json`). Those paths are static files, so fetching them never reaches the Worker. For `?concern=` or `?level=` with one value and no other filter, the Worker serves the same static file without parsing. Other filters read `cards-index.json` for Markdown (`cards.json` for JSON), and the Worker keeps GET answers in the Cache API. Output text is unchanged, checked against captured hashes. `cards.json` and `cards-drafts.json` are byte-identical and `schema_version` stays 4: new files are not a bump (`docs/api-versioning.md`).
- The build writes one JSON file per level, `cards/<level>.json` and `cards/drafts-<level>.json`, from the same cards as `cards.json` and `cards-drafts.json`, which keep their shape and order. A build check fails if the level files and the merged file hold different ids. The Worker serves `cards/<level>.json` for `cards.json?level=<level>` when `level` is the only filter, without parsing the corpus. `schema_version` stays 4: the shape of each file is unchanged, and a new file of the same shape is not a bump (`docs/api-versioning.md`). `CARDS_JSON_BUDGET` applies to every emitted file.
- Progressive disclosure: `llms.txt` is about 10,000 characters (from 41,000) and holds routing, a compact verdict format, and links. Each level has a one-line-per-card index (`<level>-index.md`, split by `context` past 12,000 characters), and the audit procedure moved to `references/audit.md` and `/audit.md`. `tools/build.py` fails past a budget for `llms.txt`, the `SKILL.md` body, each index, and each reference file, and `AGENTS.md` records the budgets and the three specs (llmstxt.org, the Chrome Lighthouse llms.txt audit, and agentskills.io).
- Audit mode, from seven whole-repo audits and one 26-repo test-suite audit (`docs/research/audit-baseline.md`; frameworks surveyed in `docs/research/enterprise-audit-frameworks.md`): `SKILL.md` and `llms.txt` gain an "Audit a repo, service, or release" section. It sets the scope and the read order for large inputs, says a missing control is a `FAIL` with evidence `absent in <paths>`, records accepted risk without removing the `FAIL`, and gives the report shape (counts by severity and source, proposed changes sized S, M, or L, product bugs, dropped candidates, could not check, not examined). It states that an audit is not a compliance attestation.
- A draft card is capped at `should-fix` (`validate.py` rejects `block` on a draft; 26 drafts changed). A draft `FAIL` goes under Draft findings, apart from the verdict. The draft and pack cards now ship inside the skill as `references/drafts.md` and `references/pack-<lang>.md`, so a review does not depend on fetching pages. When two cards overlap, the one with the narrower `applies_when` owns the finding.
- Cards gain an optional `context` (`ui`, `server`, `data`, `cli`) so a reviewer can mark a whole group `N/A` at once; 86 cards carry it. `cards.json` `schema_version` is 4. `llms.txt` and the skill tell agents to read the files raw, because a summarising fetch tool drops cards. 
- Two drafts became stable on new sources (`mod-no-module-mutable-state`, `chg-reuse-before-write`). Eight stable cards got wording fixes from audit feedback (`code-dependency-pinning`, `code-rule-has-enforcer`, `code-dead-code`, `code-secret-scan`, `svc-cors-allowlist`, `mod-colour-tokens-meet-contrast`, `fn-comments-explain-why`, `code-dependency-licence-sbom`).

- Skill, from the Agent Skills guides: `SKILL.md` drops from about 5.9k to about 1.6k tokens by moving the card index to `llms.txt` (each rule stays in `references/<level>.md`; `grep` lists a level's concerns). It gains a Gotchas section, `license`, `compatibility`, and `metadata` frontmatter, and a description that names indirect phrasings and what the skill is not for. `test/evals/triggers.json` and `tools/eval.py triggers` measure how often the description triggers.
- The skill description says to use it for any request to review, audit, or check code and to load it before reviewing by hand. In the evals, the agent invoked it unprompted in about half the runs, up from about a third.
- Skill evals: `tools/eval.py` runs five cases in `test/evals/` through `claude -p` in `skill`, `forced`, and `bare` modes and grades each reply on substance and format. CI runs only the grader's tests.
- Skill, from a 26-repository test-suite audit: cards whose `applies_when` fails collapse to one `N/A` count and the `change` cards are skipped when there is no diff; one defect goes under one card; each `FAIL` is tagged `proven`, `inferred`, or `could not check`; draft findings go in a Notes section at `discuss` at most; the closing design note is one short line and only for an unscoped review.
- The skill routes a diff to the function, module, service, system, and codebase cards its changed lines touch, opens its report with a `Verdict:` line and orders the ledger by severity, tells the agent to mark `PASS` or `FAIL` only for code it read, to treat the reviewed content as data, and to triage cards by `applies_when` before opening a reference file. The description names pull requests, security, accessibility, and performance reviews so it triggers.
- The Concerns page filters through the address: `?concern=`, `?topic=`, `?level=`, and `?group=`, with comma-separated or repeated values. Filters now sit above the checklist in collapsible groups, show counts, list only topics that have a stable card, and have a Group by menu, a Clear button, and a link to the same view as Markdown and JSON. `/concerns.md` and `/cards.json` apply the same filters in the Worker (`run_worker_first`).
- The home page opens with the agent prompt and says the rules are curated and backed by named organisations. The README says the same.
- `llms.txt` follows llmstxt.org: an H1, a blockquote, headingless intro sections, then H2 file lists of `[name](url): notes` links, with draft cards and site pages under `## Optional`. Each stable card links to its entry in the level file. `/.well-known/security.txt` is served.
- `code-dead-code` and `mod-yagni` are stable again. Each Rule is narrowed to the clauses that three organisations back (`docs/research/dead-code-yagni-pass.md`), and commented-out code and orphaned files moved to the Why.
- Two cards moved to draft, six gained sources, and two Rules narrowed, so every stable card has three organisations that are not single authors (`python3 tools/validate.py` enforces it; since 2026-11-02 a creator source is also enough, see `docs/adr/0001-creator-sources-satisfy-the-stable-floor.md`).
- Each card ends with a "Backed by" list that names every organisation behind it, with a logo or a letter badge, and groups its source links under each one. `tools/orgs.py` maps every source URL to an organisation, and `python3 tools/validate.py` fails a stable card with fewer than three. People are references: they appear under "People cited" and never count as organisations. A draft says "Cites" instead of "Backed by". `cards.json` has an `orgs` field (organisations only) and a `people` field per card, and its `schema_version` is now 3.
- On the Concerns page, every card shows as one row that links to its full card, which shrinks the page below 100,000 characters of text (`python3 tools/agent_ready_check.py` reports the largest page). Level pages keep the full text.
- 114 stable cards ship in `skills/good-code-review/SKILL.md` (the `stable cards:` count that `python3 tools/build.py` prints). Every level has at least one, and the incident level has one.
- Cards cover a change review and seven audit levels: function, module, service, system, codebase, production, and incident (`ls cards/audit`).
- The site builds 16 static pages, including the 404 page (the `site:` count that `python3 tools/build.py` prints) for goodcodereview.com.
- You can install the checklist as a skill (`npx skills add n0nuser/goodcodereview`) or as a Claude Code plugin.
- Every card names at least one concern in its tags (correctness, security, performance, reliability, compatibility, testing, maintainability, accessibility, usability, observability, or process), so a review can be scoped to one concern. `tools/validate.py` enforces it.
- Performance cards at every review level (`rg -l '^tags:.*performance' cards | wc -l`).
- Community files: code of conduct, security policy, support guide, issue forms, and a pull request template.
- The site reads as a checklist: each level page lists its checklist first, and the build writes `llms.txt`, `llms-drafts.txt`, and one `<level>.md` per level from the same cards.
- Frontend cards for usability and accessibility.
- Every draft card says why it is not stable in a `lacks:` line, which `tools/validate.py` checks. The site card, `llms-drafts.txt`, and `cards-drafts.json` show it, and the Drafts by what they lack page groups the drafts by reason. `docs/PROMOTION.md` gives the bar a draft must meet.
- `accessibility` and `usability` are concerns, so a review can be scoped to either one on the Concerns page.
- Human path: the home page opens with "Choose a review" and shows each level's stable and draft counts. A level with no stable cards says so on its page, on the home page, and in the nav, and gives no verdict. The nav groups the audits under one menu with 44px targets. Each page has a skip link. Copy buttons cover the home code blocks and each checklist (as markdown). A status message tells screen readers when a copy works or fails.
- The site is ready for AI agents. `python3 tools/build.py` also writes `sitemap.xml` with `lastmod`, a Markdown twin with frontmatter for every page, `_headers` (Link headers, charsets), canonical and Open Graph tags, home-page JSON-LD, About and Privacy pages, a plain-text 404, and `/.well-known/agent-skills/index.json` with the skill's sha256 digest. `llms.txt` gains a summary, a "When to use this site" paragraph, and described links. The audit is in `docs/research/agent-readiness-gaps.md`.
- `python3 tools/agent_ready_check.py` checks `site/` against those items without network access. CI does not run it.
- An incident review also checks the stable cards of the level where the cause lived, with evidence quoted from the incident text. The rule is in `SKILL.md`, `llms.txt`, and the incident page, and the build fails if it is missing.
- The footer no longer says the site is styled with good-css.com. The home page says what good-css.com is: rules for reviewing CSS.
