Scope: the 21 cards in `part-sec.txt`. Edited cards are judged on the diff and on whether the card still holds; new cards are judged in full. All 112 `borrowed_from` URLs were fetched once on 2026-11-06 with curl and read as text. Netflix (`netflixtechblog.com/...part-ii...`) returned 403 to curl and to WebFetch: UNFETCHED. ## code-workflow-supply-chain — ISSUES

1. **act**, check 3. The FAIL YAML does not parse. `with: { ref: ${{ github.event.pull_request.head.sha }} }` puts `{` inside a flow mapping, and PyYAML stops with `expected ',' or '}', but got '{'` (line 3, column 19). GitHub's parser rejects it as well. Fix: use block style:
   ```yaml

           ref: ${{ github.event.pull_request.head.sha }}
   ```

It never says to keep unreviewed code out of jobs that hold secrets. Fix: name GitHub, OpenSSF and GitLab in the note.
Checked: GitHub secure-use says "Workflows that use these triggers must not explicitly check out untrusted code, including from pull request forks", and also "Pin actions to a full-length commit SHA". The lockfile line in the Counterpoint matches GitHub ("supersedes SHA pinning for repositories that adopt it").

## svc-dlq — ISSUES

1. **act**, check 3 (rule 5). The FAIL and PASS HCL set `fifo_queue = true` on queues named `orders` and `orders-dlq`. SQS requires a FIFO queue name to end in `.fifo`, so `terraform apply` fails. Neither fetched AWS page states the suffix; the SQS FIFO naming rule is in the SQS developer guide's quotas and naming page (not fetched here). Fix: `name = "orders.fifo"` and `name = "orders-dlq.fifo"`.
2. **act**, check 1 (rule 3). The note counts Dropbox for the dead-letter queue and replay, but the page is a proposal: "One way to reduce this operational overhead … would be to create dead letter queues… The ATF framework could impose a maximum number of retries… We could create and expose tools…". PROMOTION rule 3 excludes plans and proposals. Counted separately, both clauses still have three organisations without Dropbox. Has a DLQ: AWS ("We alarm if there are any messages in this queue"), Notion (re-enqueue from the DLQ is "a first-class workflow") and Uber ("Dead letter messages are merged to re-enter processing"). Replay after the fix: AWS ("The benefit of the DLQ is that it lets us re-process the messages after the bug is fixed"), Notion and Uber. Netflix is UNFETCHED (403 to curl and WebFetch; web.archive.org is blocked for WebFetch). Fix: drop Dropbox from the note's count, or from `borrowed_from`, and name Notion and Uber.
3. **consider**, check 1/3. The isolation clause rests on product-behaviour pages, and those pages give the dead-letter queue as the isolation mechanism. Microsoft: "Once exceeded, the message is moved to the dead-letter queue (DLQ), and the receiver continues receiving subsequent messages from the session." Google: "consider using a dead-letter topic to prevent indefinite message holding." AWS FIFO states the blocking rule ("No additional messages from the same message group ID are returned until the first message is deleted or becomes visible again"), and its "best practice" on group IDs is about ordering across producers, not about containing poison messages. So the sources do not support the Counterpoint's "Isolation and the dead-letter queue do different jobs". The clause is also hard to fail on a standard (non-FIFO) queue. Fix: narrow the clause to "on an ordered queue, key the group or session to the unit that must stay ordered", or move it to Why. If it stays in the Rule, scope it to FIFO, session and ordering-key queues.
4. **consider**, check 3. Why says "one unacknowledged ordering key delays the others" as a fact. Google hedges it: "can potentially delay delivery of messages for other ordering keys, especially during server restarts or traffic changes." Fix: "can delay".
5. **consider**, check 6/size. The Why grew by three sentences, and the service page is 101,775 bytes. The visibility-timeout sentence repeats general queue advice and could go.

## svc-session-lifecycle — ISSUES

1. **consider**, check 3. The new Why sentence ties the planting attack to the session cookie's own `Domain` setting: "a `Domain` set to the registrable domain sends it to every subdomain, where a sibling … can plant a cookie of the same name". A sibling subdomain can plant `Domain=example.com; sid=…` even when the real session cookie is host-only. Omitting `Domain` stops the leak to subdomains, not the planting. Only the `__Host-` prefix stops planting, because a cookie named `__Host-sid` cannot carry `Domain`. Fix: split the two: "Omit `Domain`, so the cookie is not sent to subdomains. A sibling subdomain can still set a parent-domain cookie with the same name, and the `__Host-` prefix is what stops that." MDN supports it: "Prepend cookie names with either __Secure- or __Host- to prevent cookies from being overwritten", and "Set the Domain attribute only if the cookie needs to be accessible on other domains".

## svc-oauth-code-flow-binding — ISSUES

1. **act**, check 3/5. The PASS example breaks the Rule's own redirect clause. (a) `assert request.args["redirect_uri"] in REGISTERED` reads `redirect_uri` from the callback query. The authorization server does not send it there, and an attacker controls that value. (b) `exchange(request.args["code"], code_verifier=…)` sends no `redirect_uri` to the token endpoint, yet the Rule says "send the exact registered `redirect_uri`". RFC 6749 §4.1.3 requires it in the token request when the authorization request included it. Fix: `token = exchange(code, redirect_uri=REDIRECT_URI, code_verifier=session.pop("code_verifier"))`, with `REDIRECT_URI` a constant, and delete the `request.args["redirect_uri"]` line.
2. **consider**, check 1. RFC 9700's exact-match requirement binds the authorization server: "authorization servers MUST utilize exact string matching except for port numbers in localhost redirection URIs of native apps". The client-side clause the card states ("send the exact registered `redirect_uri`") draws its weight from RFC 6749 and from the OWASP and Microsoft redirect-URI guidance. Fix: say in the note that the server-side matching rule is why the client must send the registered value, or cite RFC 6749 §4.1.3.
3. **consider**, check 3. RFC 9700 makes PKCE "RECOMMENDED" for confidential clients, and lets "confidential OpenID Connect clients … use the nonce parameter … instead". The Rule requires PKCE everywhere. That is a defensible tightening, but the Counterpoint should say the card is stricter than the RFC. Also the `assert` pattern again (see account-linking 2).
Checked: S256 ("Currently, S256 is the only such method"), state or nonce (RFC 9700 and OWASP OAuth2), and ID-token `aud`/`iss`/`exp` (Google: "The value of aud in the ID token is equal to one of your app's client IDs. This check is necessary…").

## svc-webhook-replay-window — ISSUES

1. **act**, check 3. The PASS example stays replayable. `verify_hmac(body, …)` signs only the body, then the code trusts an unsigned `X-Timestamp`. An attacker replays the captured body and signature with a fresh timestamp header, and the check passes. Every cited vendor puts the timestamp inside the signature. Slack: "The signature depends on the timestamp … Concatenate the version number, the timestamp, and the request body". Svix: "The content to sign is composed by concatenating the id, timestamp and payload". Fix:
   ```python
   ts = headers["X-Timestamp"]
   if abs(time.time() - int(ts)) > 300:
       return 401
   if not verify_hmac(f"{ts}.".encode() + body, headers["X-Signature"], secret):
       return 401
   ```
   Also add "and the timestamp is covered by the signature" to the Rule or the Why. Without it the Rule can be met by a check that does nothing.
2. **act**, check 1. Stripe's URL is dead for this claim: it redirects to "Manage webhook endpoints", which mentions neither tolerance nor replay. That leaves Svix ("compare this timestamp against your system timestamp and make sure it's within your tolerance in order to prevent timestamp attacks"), Slack ("verify that the timestamp does not differ from local time by more than five minutes … It could be a replay attack") and IETF, which is weak (next finding). Fix: replace it with Stripe's current verification page (`docs.stripe.com/webhooks#verify-events`, not checked here). Do not use Standard Webhooks as the third organisation: Svix started that spec, so it is not independent of Svix under "Count organisations".
