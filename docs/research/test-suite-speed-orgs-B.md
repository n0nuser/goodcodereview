# Test-suite speed, language-neutral practices (B1-B6): organisation sources

Fetched 2026-11-05 with WebFetch and with `curl` + `html2text` (full page text). Text in quote marks is verbatim from the fetched page; rows without quote marks are paraphrase. Each row gives the URL, the org, what the page states, and the claim id it backs. Organisation names follow `tools/orgs.py`.

Excluded by the brief and not repeated: `docs.pytest.org`, `docs.python.org`, `github.com/zupo/awesome-pytest-speedup`.

## B1. Measure before optimising: profile the slowest tests / setup time and track suite duration

1. https://firefox-source-docs.mozilla.org/testing/xpcshell/index.html (org: Mozilla). The xpcshell docs give a per-test `requesttimeoutfactor` for tests that are disproportionately slow on one platform, and explicitly tell authors not to reach for it when the test itself is the problem: "You should **not** use this for tests that are slow due to inefficient test code or unnecessary waits. Consider profiling and refactoring such tests instead." They reserve the factor for platform slowness, "only use it when a specific test needs extra time beyond what the platform factor already provides." Backs B1.
2. https://thoughtbot.com/blog/introducing-test-budget (org: thoughtbot). Their Test Budget tool "reads your test run timings and reports when they exceed a configured budget. It doesn't change how your tests run. It just tells you when they're too slow (before it gets worse)." The proposed budgets come from the project's own measurements: "The total suite budget is set 10% above your current total, giving you headroom", and per-test-type budgets come from the 99th percentile because "Your slowest 1% of tests are the ones you need to fix." Backs B1 and B2.
3. https://circleci.com/docs/guides/insights/insights-tests/ (org: CircleCI; vendor documentation for its own product). "Use CircleCI test Insights to analyze your test performance within the most recent executions and identify opportunities for test optimization." The listed signals include "Slow run times in test suite", and a "Slowest tests" view ranks the individual tests that take longest. Backs B1. Weaker than the other two: it describes a product feature rather than a team's practice.

## B2. Enforce a time budget in CI, or keep fast tests separate from slow ones

4. https://shopify.engineering/test-budget-time-constrained-ci-feedback (org: Shopify). Shopify's Test Infrastructure team, on a 170,000-test monolith, built a "test budget: a fixed amount of time for tests to run". Tests are ordered so failures surface early, and execution is cut off at the bound: "The time budget is an upper bound. The CI system executes the tests up to that time bound." Their headline result was "we were able to find failures after we had run only 70% of the test-selection suite". Backs B2 (and the selection half backs B6).
5. https://thoughtbot.com/blog/introducing-test-budget (org: thoughtbot). Budgets are set at two levels, and the suite-level example is "your entire test suite should run in under 10 minutes". Going over a budget is a violation that fails `test_budget audit`; slow tests must be allowlisted with a reason, and allowlist entries carry an expiry date so "the test starts failing the audit again". They argue for a tight budget: "Way too many teams are comfortable with 10+ minute test suites. That is an awful lot of time to wait for feedback." Backs B2.
6. https://abseil.io/resources/swe-book/html/ch11.html (org: Google). Google classifies every test by size and enforces the classification: "Having precise definitions of test sizes has allowed us to create tools to enforce them. Enforcement enables us to scale our test suites and still make certain guarantees about speed, resource utilization, and stability." The example is the Java security manager that "will cause all tests tagged as small to fail if they attempt to do something prohibited, such as establish a network connection." Engineers are encouraged "to always write the smallest possible test", aiming at about 80% small tests. Backs B2 (enforced size/time classification) and B3/B4.
7. https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html (org: Google). The post separates the fast bulk of the suite from the slow tail: unit tests are fast because "one tenth of a second is considered slow for unit tests", and it recommends "a 70/20/10 split: 70% unit tests, 20% integration tests, and 10% end-to-end tests" so end-to-end tests stay a small minority. Backs B2 (keep fast tests the majority; slow tests few).
8. https://microsoft.github.io/code-with-engineering-playbook/automated-testing/ (org: Microsoft). Their team practice: "We write unit tests (tests without external dependencies) that can run before every PR merge to validate that we don't have regressions", while "We write Integration tests/E2E tests that test the whole system end to end, and run them regularly." The fast tests gate every merge; the slow end-to-end tests run on a separate cadence. Backs B2 and B3.

## B3. Keep unit tests off the real network and disk (fakes, stubs, in-memory)

9. https://abseil.io/resources/swe-book/html/ch11.html (org: Google). Small tests "aren't allowed to sleep, perform I/O operations, or make any other blocking calls. This means that small tests aren't allowed to access the network or disk", and code that needs those operations "requires the use of test doubles ... to replace the heavyweight dependency with a lightweight, in-process dependency." The stated purpose is speed and determinism, and "A test that runs on a single process and never makes blocking calls can effectively run as fast as the CPU can handle." All tests should also strive to be hermetic. Backs B3.
10. https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices (org: Microsoft). A good unit test is "Fast" and "Isolated": "Unit tests should take little time to run. Milliseconds", and "Unit tests are standalone, can run in isolation, and have no dependencies on any outside factors, such as a file system or database." Under "Avoid infrastructure dependencies": "The dependencies make the tests slow and brittle and should be reserved for integration tests", with a separate test project so the unit-test project has no references to infrastructure packages. Backs B3.
11. https://docs.spring.io/spring-framework/reference/testing/unit.html (org: Spring). Unit tests are "JUnit or TestNG tests, with objects instantiated by using the `new` operator, without Spring or any other container", using mock objects; "you can test service layer objects by stubbing or mocking DAO or repository interfaces, without needing to access persistent data while running unit tests." And "True unit tests typically run extremely quickly, as there is no runtime infrastructure to set up." Backs B3 and B4.

## B4. Do not give every test the whole database/environment

12. https://docs.djangoproject.com/en/6.1/topics/testing/tools/ (org: Django Software Foundation). `SimpleTestCase` "disallows database queries by default", so a test class that does not need the database does not get one; the docs advise "If your Django application doesn't use a database, use `SimpleTestCase`." Where a group of tests does need data, it goes in `setUpTestData()`, created "once for the whole `TestCase`", and "This technique allows for faster tests as compared to using `setUp()`." Backs B4.
13. https://abseil.io/resources/swe-book/html/ch11.html (org: Google). The size classification is what stops every test getting the full environment: "you can't run a third-party program such as a database as part of your test" in a small test, and a medium test "aren't allowed to make network calls to any system other than localhost". A test is labelled by what it actually needs, and the heavier resource is only granted to the larger sizes. Backs B4.
14. https://docs.spring.io/spring-framework/reference/testing/unit.html (org: Spring). Mocking or stubbing "DAO or repository interfaces" lets a service-layer test run "without needing to access persistent data", i.e. no database at all for tests that do not exercise persistence. Backs B4.

## B5. Parallelise with per-worker isolated database; shard CI by recorded timings

15. https://docs.djangoproject.com/en/6.1/topics/testing/advanced/ (org: Django Software Foundation). The test runner's `--parallel` option "specifies the number of processes", and "Each process gets its own database." Test classes that cannot run in parallel because they share a resource can be marked with `SerializeMixin` to run sequentially. Backs B5 (isolation half).
16. https://guides.rubyonrails.org/testing.html (org: Ruby on Rails). "Running tests in parallel reduces the time it takes your entire test suite to run." When parallelising, "Active Record automatically handles creating a database and loading the schema into the database for each process. The databases will be suffixed with the number corresponding to the worker", for example `test-database-0` and `test-database-1` for two workers; `PARALLEL_WORKERS` sets the count, and the runner only parallelises above a threshold (the CLI output says "parallelization threshold is 50"). Backs B5 (isolation half).
17. https://circleci.com/docs/guides/optimize/parallelism-faster-jobs/ (org: CircleCI; vendor documentation for its own product). Splitting a suite across parallel executors is presented as the way to cut testing time, and `--split-by=timings` uses history: "the split points are calculated based on historic timing data" so the containers get comparable work. Backs B5 (timing-shard half).

## B6. Run only the tests affected by a change; rerun failures first; full suite in CI

18. https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/ (org: Meta). Predictive test selection "needs to run only a small subset of tests in order to reliably detect faulty changes". It was deployed for more than a year and caught "more than 99.9 percent of all regressions before they are visible to other engineers". Backs B6.
19. https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops (org: Microsoft). Test Impact Analysis "automatically selects only the subset of tests required to validate the code being committed", and the selection "includes existing impacted tests, previously failing tests, and newly added tests". It has a "Safe fallback": for changes it cannot reason about (for example HTML or CSS edits) it "falls back to running all tests". Backs B6, including the rerun-previously-failing clause.
20. https://shopify.engineering/spark-joy-by-running-fewer-tests (org: Shopify). On a 150,000-test suite that took 30-40 minutes across hundreds of containers, "it became apparent that the right solution was to only run the tests related to the code change." They build a file-to-test map from recorded call graphs, run the selected tests on each pull request, and keep the full suite: "we run the full test suite every deploy", asynchronously, so a pull request is not blocked. The selection rate averages about 60%, and "About 40% of builds run fewer than 20% of tests". Backs B6.
21. https://circleci.com/docs/guides/test/rerun-failed-tests/ (org: CircleCI; vendor documentation for its own product). Rerunning the whole workflow "executes all tests, including tests that passed, which prolongs time-to-feedback and consumes credits unnecessarily"; rerunning failed tests runs "a subset of tests (your failed tests)" from the same commit instead. Backs B6 (rerun-failures-first half).

## Also read, no rule

- https://docs.djangoproject.com/en/6.1/topics/testing/advanced/ (Django). The runner documents `--durations N` ("Show the N slowest test cases") and `--timing` (outputs timings "including database setup and total run time"). A feature reference, not a recommendation, so it does not count on its own; it is the mechanism a B1 instruction would point at in Django.
- https://engineering.atspotify.com/2018/01/testing-of-microservices (Spotify). Fetched for B3/B4 but it argues the opposite: Spotify's integration tests "spin up a database, populate it, start the service, and query the actual API", trading speed ("The suite goes from milliseconds to a few seconds") for confidence. It states that test feedback should be "fast, accurate, reliable and predictable", nothing about fakes or in-memory databases. Excluded from B3/B4.

## Counts

- B1 (profile the slowest tests, track duration): 3 organisations - Mozilla, thoughtbot, CircleCI. Medium-high confidence. Mozilla and thoughtbot are practice statements; CircleCI is product documentation, so if vendor docs are excluded this drops to 2.
- B2 (time budget in CI, or fast/slow separation): 4 - Shopify, thoughtbot, Google, Microsoft. High confidence. The explicit "stop/fail at a time bound" half rests on Shopify and thoughtbot; the "keep fast tests the majority" half on Google (test sizes, 70/20/10) and Microsoft (unit tests before every merge, E2E on a separate cadence).
- B3 (off the real network and disk): 3 - Google, Microsoft, Spring. High confidence. All three say the dependency is what makes the test slow and prescribe doubles or mocks.
- B4 (no full database/environment for every test): 3 - Django Software Foundation, Google, Spring. High confidence. Django and Spring are framework docs stating the default and the recommended split; Google states the size rule that forbids a database in a small test.
- B5 (per-worker isolated database, timing shards): 3 - Django, Rails, CircleCI. High confidence on the isolation half (Django and Rails both state it as default behaviour); the timing-shard half rests on CircleCI alone.
- B6 (affected tests only, rerun failures, full suite in CI): 4 - Meta, Microsoft, Shopify, CircleCI. High confidence. Caveat: all four describe selection in CI or presubmit with the full suite retained, not "run only affected tests locally"; the local-run framing of B6 is not directly sourced here. The "full suite still runs" half is explicit in Shopify and Microsoft (safe fallback).

Two organisations carry several claims: CircleCI backs B1, B5 and B6, and it is a CI vendor documenting its own features. Excluding vendor docs leaves B1 and B5 at 2 organisations each. Google appears on B2, B3 and B4 through two pages (the SWE book and the testing blog), and Microsoft on B2 and B3 through two pages (the engineering playbook and the .NET docs); per `docs/PROMOTION.md` each still counts once.
