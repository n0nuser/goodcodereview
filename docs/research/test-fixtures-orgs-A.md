# Test fixtures built once: independent-organisation sources (A1 and A2)

Fetched 2026-11-05. Every row below is a page I fetched and read; the wording is a paraphrase unless it is in quote marks. A1 is "build the expensive test state once per module, session, suite or test binary". A2 is "reset per test cheaply: roll back a transaction or savepoint, or truncate". A1 is the Rule of `py-test-fixtures-built-once`; A2 is that card's reset clause and the subject of a separate card. Count organisations, not pages: two pages from one project are one organisation.

1. https://docs.djangoproject.com/en/5.1/topics/testing/tools/ (org: Django Software Foundation). `TestCase` wraps each test in two nested `atomic()` blocks, one for the class and one for the test, and `setUpTestData()` creates class-level data "once for the whole `TestCase`". "This technique allows for faster tests as compared to using `setUp()`." The reset is a rollback: "it encloses the test code in a database transaction that is rolled back at the end of the test". `TransactionTestCase` is the slower alternative that truncates tables. Backs A1 and A2.

2. https://guides.rubyonrails.org/testing.html (org: Rails / Ruby on Rails project). "By default, Rails automatically wraps tests in a database transaction that is rolled back once completed. This makes tests independent of each other and means that changes to the database are only visible within a single test." Fixtures are the predefined dataset loaded before the tests run, so the transaction is the per-test reset rather than a rebuild. Tests can opt out with `self.use_transactional_tests = false`. Backs A2 (and A1 for the fixture dataset).

3. https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/tx.html (org: Spring / Broadcom). "Annotating a test method with `@Transactional` causes the test to be run within a transaction that is, by default, automatically rolled back after completion of the test." Test methods not annotated run outside a transaction; `@Commit` and `@Rollback` change the default. Backs A2.

4. https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/ctx-management/caching.html (org: Spring / Broadcom). A loaded `ApplicationContext` "is cached and reused for all subsequent tests that declare the same unique context configuration within the same test suite". "This means that the setup cost for loading an application context is incurred only once (per test suite), and subsequent test execution is much faster." The cache is static, so forking a new JVM per test class disables it and "the build process runs significantly more slowly". `@DirtiesContext` forces a rebuild. Backs A1.

5. https://laravel.com/docs/12.x/database-testing (org: Laravel). `RefreshDatabase` "does not migrate your database if your schema is up to date. Instead, it will only execute the test within a database transaction." The alternatives that rebuild — `DatabaseMigrations` and `DatabaseTruncation` — are "significantly slower than the `RefreshDatabase` trait". Backs A1 and A2.

6. https://hexdocs.pm/ecto_sql/Ecto.Adapters.SQL.Sandbox.html (org: Ecto / Elixir Ecto project). The sandbox is "A pool for concurrent transactional tests". On checkout "the sandbox will wrap the connection in a transaction by default", and the FAQ states that "the SQL Sandbox mode rolls back transactions". An owner process holds one connection per test; the schema is not rebuilt. Backs A2.

7. https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#joining-a-session-into-an-external-transaction-such-as-for-test-suites (org: SQLAlchemy). The documented test recipe opens a `Connection` transaction, binds the `Session` with `join_transaction_mode="create_savepoint"`, and rolls the outer transaction back in `tearDown`: "When the test tears down, the external transaction is rolled back so that any data changes throughout the test are reverted." The rationale is "a test suite that allows ORM code to work freely with a `Session`, including the ability to call `Session.commit()`, where afterwards the entire database interaction is rolled back." "The above recipe is part of SQLAlchemy's own CI". Backs A2.

8. https://pytest-django.readthedocs.io/en/latest/database.html (org: pytest-django / pytest-dev). "By default `pytest-django` will set up Django databases the first time a test needs them. Once setup, a database is cached to be used for all subsequent tests and rolls back transactions, to isolate tests from each other." `--reuse-db` keeps the test database between runs, which "will allow much faster startup time for tests". The docs also show a session-scoped `django_db_setup` that copies a pre-migrated database with `CREATE DATABASE ... TEMPLATE`, and a session fixture that loads seed data once. `TransactionTestCase`-style tests flush between tests and are "much slower to set up". Backs A1 and A2.

9. https://learn.microsoft.com/en-us/ef/core/testing/testing-with-the-database (org: Microsoft / EF Core). "In most simple cases, your test suite has a single database that's shared between multiple tests across multiple test classes, so we need some logic to make sure the database is created and seeded exactly once during the lifetime of the test run." The xUnit class fixture does the create/seed once behind a static flag. For writing tests, "One common technique to isolate writing tests is to wrap the test in a transaction, and to have that transaction rolled back at the end of the test." Tests that must commit get a separate database and an explicit `Cleanup()` after each test. Backs A1 and A2.

10. https://alloy.ai/speeding-up-integration-tests-db (org: Alloy.ai). Their old per-test cycle was: create a unique Postgres database, run all Flyway migrations, run the test, drop the database. "Dropping, recreating, and migrating a database takes somewhere on the order of 10 seconds", and in April 2020 "our integration test suite already took 14 minutes to run single-threaded in CI, with only 78 integration test cases". They changed to wrapping each test in a transaction and rolling it back, "cutting them down to 8 minutes single-threaded in CI". They keep "a dedicated database per test suite, and as such migrates once per test suite as well". Caveats: a shared database across all suites caused deadlocks; tests that assert on transaction behaviour or use multiple connections do not fit. Backs A1 and A2, with numbers.

11. https://docs.gitlab.com/development/testing_guide/best_practices/ (org: GitLab). GitLab's testing standard says the suite "can take hours to run" without parallelisation, and recommends `let_it_be`, which "creates an object one time for all of the examples in the same context" and "can dramatically speed up tests that create database models". The variant for objects a test mutates, `let_it_be_with_reload`, still creates once but "after each example, the database changes are rolled back". `before_all` setup runs once per context and is rolled back when the context ends. Backs A1 and A2.

12. https://shopify.engineering/faster-shopify-ci (org: Shopify). Shopify's CI runs "more than 170,000 tests", which take "more than 41 hours to run all tests on a single machine". To avoid rebuilding the Rails database on every job, they hash `structure.sql` and `db/migrate`: "If the hash is the same as our cache, we don't need to load the Rails app and run db:migrate." With that and parallel steps the dependency job went "from 5 minutes to around 3 minutes". The post's overall result is p95 CI "from 45 minutes to 18". This is CI-level reuse of a built state, adjacent to A1 rather than a per-suite fixture, but it is the same "do not rebuild what has not changed" decision. Backs A1 (weakly).

13. https://jestjs.io/docs/configuration#globalsetup-string (org: Jest / OpenJS Foundation). `globalSetup` names a module whose function "will be triggered once before all test files", and the docs' example starts a `mongod` process there and stops it in `globalTeardown`. That is the supported place to build a shared external dependency once for the whole run; the docs warn that values set in `globalSetup` cannot be read from the test suites, so the shared thing must be a service or a file, not an in-process object. Backs A1.

14. https://pkg.go.dev/testing#hdr-Main (org: Go / Go project). When a test package defines `TestMain(m *testing.M)`, "the generated test will call TestMain(m) instead of running the tests or benchmarks directly", and "TestMain runs in the main goroutine and can do whatever setup and teardown is necessary around a call to m.Run". This is the per-binary hook for a container, server or database built once for the package; the docs call it "a low-level primitive" and do not claim a speed number. Backs A1 (mechanism, not a measured claim).

15. https://java.testcontainers.org/features/reuse/ (org: Testcontainers). "The Reusable feature keeps the containers running and next executions with the same container configuration will reuse it." Reuse needs `withReuse(true)` plus an environment or properties opt-in, and the configuration must be identical. The docs also say "Reusable containers are not suited for CI usage" and that the feature is experimental, so this is reuse across local runs rather than the in-suite singleton the card wants; a singleton started in `@BeforeAll` is the in-suite form. Backs A1 (with a CI caveat).

Also read, no rule:

- https://cal.com/blog/how-we-cut-our-ci-wall-time-from-30-minutes-to-5-minutes (org: Cal.com). Read: faster runners, dependency caching and test sharding. It does not describe building a fixture once and resetting per test, so it does not back A1 or A2.
- https://gitlab.com/gitlab-org/gitlab/-/issues/515776 (org: GitLab). Read: a plan to build the database once per pipeline and restore it with `pg_dumpall`, because `setup_db` costs about 1m10s in each of about 150 RSpec jobs. A plan is excluded by the source rules; the GitLab docs entry above is the practice.

Count, distinct organisations:

- A1: Django, Rails, Spring, Laravel, pytest-django, Microsoft, Alloy.ai, GitLab, Shopify, Jest, Go, Testcontainers = 12. Strongest are Django, Spring, Laravel, pytest-django, Microsoft, Alloy.ai and GitLab. Go, Jest and Testcontainers document the once-per-run mechanism rather than a measured speed-up; Shopify is CI-level reuse, not a per-suite fixture.
- A2: Django, Rails, Spring, Laravel, Ecto, SQLAlchemy, pytest-django, Microsoft, Alloy.ai, GitLab = 10. All ten state rollback or truncation as the per-test reset in their own words; Django, Rails and Laravel also compare it with the slower rebuild/truncate path.
- Overlap: nine organisations appear in both lists. Confidence high for the framework and library docs (they are the maintainers' own guidance), high for Alloy.ai and Microsoft (a team describing what it changed and the result), high for GitLab's docs, medium for Go/Jest/Testcontainers (mechanism only) and Shopify (adjacent).
