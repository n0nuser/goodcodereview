## G1. Request smuggling and request-framing disagreement

**Candidate Rule.** Reject a request whose framing is ambiguous between hops, parse it strictly, and close the connection instead of forwarding it.

**Level.** service (system when the chain has more than one proxy hop). **Tool gate.** none found; the AWS attribute below is a configuration control, not a linter.

**Existing card.** None. No card mentions `Content-Length`, `Transfer-Encoding`, chunked framing, desync or request smuggling. `fn-bounded-read-fails-at-cap` bounds how much a reader takes, not where one message ends.

**FAIL/PASS.** FAIL: a proxy forwards a request carrying both `Content-Length` and an obfuscated `Transfer-Encoding`, and the backend keeps the connection alive. PASS: both fields on one request are rejected with 400 (or stripped, then the connection closed), whitespace before the colon is rejected, and an HTTP/2 front end does not downgrade unchecked.

1. https://www.rfc-editor.org/rfc/rfc9112.html (org: IETF). Section 6.3 makes one field win but calls the combination an attack: "If a message is received with both a Transfer-Encoding and a Content-Length header field, the Transfer-Encoding overrides the Content-Length. Such a message might indicate an attempt to perform request smuggling ... and ought to be handled as an error." It then bounds forwarding: "An intermediary that chooses to forward the message MUST first remove the received Content-Length field and process the Transfer-Encoding (as described below) prior to forwarding the message downstream." Section 6.2 states the sender side: "A sender MUST NOT send a Content-Length header field in any message that contains a Transfer-Encoding header field." It also names leniency as the cause: "lenient parsing can result in request smuggling security vulnerabilities if there are multiple recipients of the message and each has its own unique interpretation of robustness" (Section 2.2), and requires strictness on a known obfuscation: "A server MUST reject, with a response status code of 400 (Bad Request), any received request message that contains whitespace between a header field name and colon" (Section 5.1). Backs G1.
2. https://portswigger.net/web-security/request-smuggling (org: PortSwigger). The prevention list is concrete: "Use HTTP/2 end to end and disable HTTP downgrading if possible." and "Make the front-end server normalize ambiguous requests and make the back-end server reject any that are still ambiguous, closing the TCP connection in the process." It adds "Never assume that requests won't have a body." and, for the downgrade path, "reject requests that contain newlines in the headers, colons in header names, and spaces in the request method." Backs G1.
3. https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html (org: AWS). The load balancer exposes a framing-hardening setting with a documented default: "`routing.http.desync_mitigation_mode` ... Determines how the load balancer handles requests that might pose a security risk to your application. The possible values are `monitor`, `defensive`, and `strictest`. The default is `defensive`." The page ties it to this class: "The `routing.http.desync_mitigation_mode` attribute was added to provide more comprehensive protection from HTTP desync for your applications." Backs G1.
4. https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/security-considerations?view=aspnetcore-10.0 (org: Microsoft). The server states its default behaviour: "When both Transfer-Encoding and Content-Length are present, Transfer-Encoding takes precedence. The Content-Length header is removed and preserved as `X-Content-Length` for diagnostic purposes. The connection is closed after the response to prevent pipeline-based smuggling." It also rejects duplicates and a non-final chunked coding: "Multiple Content-Length headers are rejected, even when the repeated values are identical." and "If Transfer-Encoding is present but the final coding isn't `chunked`, the request is rejected." Backs G1.
5. https://nodejs.org/api/http.html (org: OpenJS Foundation). Lenient parsing is opt-in with a warning: "`insecureHTTPParser` ... Using the insecure parser should be avoided." with `Default: false`. Header-value validation likewise defaults to the strict setting: "`httpValidation` ... `'strict'`: Strictest validation; rejects any non-ASCII or control characters in header values." with `Default: 'strict'`. Backs G1.

**Verdict.** 5 organisations for the whole rule (IETF, PortSwigger, AWS, Microsoft, OpenJS). Per clause: "reject or close on both framing fields" has IETF, Microsoft, PortSwigger and AWS = 4; "parse strictly, no leniency flag" has IETF, OpenJS and PortSwigger = 3; "normalize at the front end and reject at the back end" has PortSwigger and IETF Section 5.1 = 2; "no HTTP/1 downgrade" has PortSwigger only = 1. Confidence high on the rule, low on the downgrade clause, which should stay in Why.

## G2. Web cache poisoning through unkeyed inputs

**Candidate Rule.** Key every request input that changes the response, and never let a value that is not in the cache key reach the response body.

**Level.** service. **Tool gate.** none found; cache-key configuration is the control.

**Existing card.** `svc-api-cache-control` (stable) covers `Cache-Control` and `Vary`, which is the origin's half. Missing: the cache key itself, unkeyed headers and GET bodies reaching the body, and the rule that a CDN must not be left with vendor defaults that key less than the origin assumes.

**FAIL/PASS.** FAIL: the origin echoes `X-Forwarded-Host` or a GET body into the page while the CDN keys only on path. PASS: the response varies only on keyed inputs, the cache key includes the header or cookie that changes the body, and unnecessary request headers are disabled at the edge.

1. https://portswigger.net/web-security/web-cache-poisoning (org: PortSwigger). The prevention section refuses both the cheap fixes: "If a header isn't needed for the site to work, then it should be disabled." and "If you are considering excluding something from the cache key for performance reasons, rewrite the request instead." It also names GET bodies: "Don't accept fat `GET` requests." Backs G2.
2. https://developers.cloudflare.com/cache/cache-security/avoid-web-poisoning/ (org: Cloudflare). The rule is stated twice: "Do not rely on values in HTTP headers if they are not part of your cache key." and "Do not include untrusted header values in your response body." It extends the same logic to the body: "GET request bodies should be considered untrusted and should not modify the contents of a response." Its first instruction is "Only cache files that are truly static". Backs G2.
3. https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-the-cache-key.html (org: AWS). The key must carry what the origin varies on: "When a value in the viewer request determines the response that your origin returns, you should include that value in the cache key." The page also warns against over-keying, which is why the earlier clause is about correctness, not size: "include only the minimum necessary values in the cache key." Backs G2.
4. https://learn.microsoft.com/en-us/azure/frontdoor/front-door-caching (org: Microsoft). Query-string handling is an explicit cache-key decision: with ignore mode, "Future requests for the asset that are served from the Front Door environment ignore the query strings until the cached asset expires"; with include mode, "each request with a unique URL, including the query string, is treated as a unique asset with its own cache". Its warning is the class in one line: "with misconfiguration you can inadvertently cache user specific data that can be shared by multiple users resulting privacy incidents." Backs G2.
5. https://developers.cloudflare.com/cache/how-to/cache-keys/ (org: Cloudflare). The vendor's own advice for its key: "When URL normalization is enabled, we recommend also enabling Normalize URLs to origin ... This helps ensure the URL in the cache key matches the URL sent to the origin, preventing cache poisoning and ensuring consistent behavior." Its default key includes `x-forwarded-host`, `x-host`, `x-original-url` and `forwarded` (paraphrase of the four-item list), which is exactly the class of unkeyed input other caches leave out. Backs G2.

**Verdict.** 4 organisations for the whole rule (PortSwigger, Cloudflare, AWS, Microsoft). Per clause: "key everything that changes the response" has AWS, Cloudflare and Microsoft's include mode = 3; "don't reflect unkeyed headers/bodies" has Cloudflare and PortSwigger = 2; "cache only static assets" has Cloudflare and PortSwigger = 2; "rewrite instead of excluding from the key" has PortSwigger only = 1. Confidence high on the keying clause, medium on the rest.

## G3. Cache deception and caching private or authenticated responses

**Candidate Rule.** Mark every authenticated or user-specific response `private` or `no-store`, and make the cache refuse a response whose type does not match the path it was requested at.

**Level.** service. **Tool gate.** none found. Cloudflare's Cache Deception Armor (`cache_deception_armor`) is a configuration control.

**Existing card.** `svc-api-cache-control` (stable) already has the first half as its Rule: "use `private` or `no-store` for user-specific data". Missing: cache deception proper (a dynamic path served as `/foo.css` and cached by extension), the rule that a CDN's cache rule must not override the origin header, and the path-interpretation agreement between origin and cache. A new card would repeat the existing Rule, so the choice is to extend that card or add a narrow one for the deception half.

**FAIL/PASS.** FAIL: `/account` returns private HTML, the CDN caches `/account/x.css` by extension, and the response carries no `Cache-Control`. PASS: authenticated responses are `private, no-store`, the CDN's cache rule keeps that header, and a cache rule checks the response `Content-Type` against the URL extension before storing.

1. https://portswigger.net/web-security/web-cache-deception (org: PortSwigger). Four prevention steps, all checkable: "Always use `Cache-Control` headers to mark dynamic resources, set with the directives `no-store` and `private`."; "Configure your CDN settings so that your caching rules don't override the `Cache-Control` header."; "Activate any protection that your CDN has against web cache deception attacks."; and "Verify that there aren't any discrepancies between how the origin server and the cache interpret URL paths." It names the control: "For example, Cloudflare's Cache Deception Armor." Backs G3.
2. https://cloud.google.com/cdn/docs/caching (org: Google). "To prevent private information from being cached in Cloud CDN caches, do the following: ... Include a `Cache-Control: private` header in responses that shouldn't be stored in Cloud CDN caches, or a `Cache-Control: no-store` header in responses that shouldn't be stored in any cache, even a web browser's cache." The authenticated case is explicit: "For origin (cache fill) requests that include the `Authorization` request header, Cloud CDN only caches responses that include the `public`, `must-revalidate`, or `s-maxage` cache control directives ... This prevents accidentally caching per-user content and content that requires authentication." Backs G3.
3. https://developers.cloudflare.com/cache/cache-security/cache-deception-armor/ (org: Cloudflare). The attack is the origin serving a dynamic path under a static-looking one: "Because the path ends in `.jpg`, Cloudflare caches the response by default." The remedy is a type check: "the rule will verify a URL's extension matches the returned `Content-Type`." and "When a mismatch that could result in a Web Cache Deception attack is found, Cloudflare does not cache the response." Backs G3.
4. https://learn.microsoft.com/en-us/azure/frontdoor/front-door-caching (org: Microsoft). Authenticated traffic is kept out of the cache by route design: "dynamic assets, such as authenticated API endpoints, shouldn't be cached to prevent the leakage of personal information. It's recommended to have separate routes for static and dynamic assets, with caching disabled for the latter." The header behaviour matches: "Requests that include authorization header won't be cached, unless the response contains a Cache-Control directive that allows caching. The following Cache-Control directives have such an effect: must-revalidate, public, and s-maxage." Backs G3.

**Verdict.** 4 organisations for the combined rule (PortSwigger, Google, Cloudflare, Microsoft), on top of `svc-api-cache-control`'s existing OWASP, IETF and Zalando support for `private`/`no-store`. Per clause: "mark dynamic responses private/no-store" has four here plus the existing card = 7; "the CDN must not override the origin" has PortSwigger and Microsoft = 2 (and Cloudflare says an Edge Cache TTL rule *can* override it — see counter-evidence); "match extension to `Content-Type`" has Cloudflare and PortSwigger = 2; "agree on path interpretation" has PortSwigger only = 1. Confidence high on the `private`/`no-store` clause, medium on the deception-specific clauses.

## G4. Trusting Host and X-Forwarded-* headers

**Candidate Rule.** Build absolute URLs and reset links from configured values, and accept a Host or forwarded header only from an allowlist or a trusted proxy.

**Level.** service. **Tool gate.** none found (framework host filtering is a runtime control).

**Existing card.** None for this class. `fn-redirect-target-allowlist` (stable) checks the *target* of a redirect, not how a URL or a reset link is built, and `sys-ssrf` covers the server following a URL, not the server publishing one. Missing: password-reset poisoning, absolute-URL building from `Host`, duplicate `Host`, `X-Forwarded-Host`, and the trusted-proxy list.

**FAIL/PASS.** FAIL: `link = f"https://{request.headers['Host']}/reset?token={token}"` with no host allowlist. PASS: `link = f"{settings.PUBLIC_BASE_URL}/reset?token={token}"`, `ALLOWED_HOSTS`/`AllowedHosts` set, and forwarded headers consumed only from `KnownProxies`/`KnownNetworks`.

1. https://portswigger.net/web-security/host-header (org: PortSwigger). The strongest form of the rule is not to use the value: "To prevent HTTP Host header attacks, the simplest approach is to avoid using the Host header altogether in server-side code." For the reset link: "you should require the current domain to be manually specified in a configuration file and refer to this value instead of the Host header. This approach would eliminate the threat of password reset poisoning, for example." And the override header: "check that you do not support additional headers that may be used to construct these attacks, in particular `X-Forwarded-Host`. Remember that these may be supported by default." Backs G4.
2. https://www.fastly.com/learning/security/what-are-http-host-header-attacks (org: Fastly). Under "Perform strict validation on Host header values": "Validate the Host header is in an allowed list of values." and "Validate there is only one Host header. Duplicate Host headers can sometimes be used to bypass the validation if the validation and usage of the header end up pulling different values from the request." It adds "Avoid using Host header alternatives and overrides such as X-Host or X-Forwarded-Host". Backs G4.
3. https://docs.djangoproject.com/en/5.2/ref/settings/ (org: Django Software Foundation). `ALLOWED_HOSTS` is the allowlist with an empty default: "A list of strings representing the host/domain names that this Django site can serve. This is a security measure to prevent HTTP Host header attacks, which are possible even under many seemingly-safe web server configurations." The bypass is named: "This validation only applies via `get_host()`; if your code accesses the `Host` header directly from `request.META` you are bypassing this security protection." The forwarded header is opt-in per trusted proxy: "This should only be enabled if a proxy which sets this header is in use." (`USE_X_FORWARDED_HOST`, default `False`). Backs G4.
4. https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/host-filtering (org: Microsoft). The default is open, so the check is the configured value: "`Host` headers aren't validated." and "Host-filtering middleware is disabled by default. To enable the middleware, define an `AllowedHosts` key in `appsettings.json`/`appsettings.{Environment}.json`." Backs G4.
5. https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer (org: Microsoft). Forwarded values are trusted only from known peers: `KnownNetworks` is "Address ranges of known networks to accept forwarded headers from", with a single loopback entry as the default, and `KnownProxies` does the same by exact address. The page ties `X-Forwarded-Host` to the attack: "an elevation-of-privileges vulnerability that affects systems where the proxy doesn't validate or restrict Host headers to known good values". Backs G4.
6. https://www.rfc-editor.org/rfc/rfc9112.html (org: IETF). Section 3.2 requires a rejection rather than a guess: "A server MUST respond with a 400 (Bad Request) status code to any HTTP/1.1 request message that lacks a Host header field and to any request message that contains more than one Host header field line or a Host header field with an invalid field value." Backs G4.

**Verdict.** 5 organisations for the whole rule (PortSwigger, Fastly, Django, Microsoft, IETF). Per clause: "build absolute URLs from configuration" has PortSwigger and Fastly (relative URLs / server-side config) = 2, plus Django's allowlist as the weaker form; "allowlist the Host and reject unknown" has PortSwigger, Fastly, Django and Microsoft = 4; "reject duplicate Host" has IETF and Fastly = 2; "honour forwarded headers only from a trusted proxy" has Django, Microsoft, PortSwigger and Fastly = 4. Confidence high on the rule, medium on the reset-link clause.

## G5. Response header injection and CRLF in headers and redirects

**Candidate Rule.** Build every response header value through the framework API, and reject or encode CR and LF in any value that comes from the request.

**Level.** function. **Tool gate.** none found; Node and Django throw at runtime, which is a guard, not a linter.

**Existing card.** None. `fn-redirect-target-allowlist` (stable) validates where a redirect points; it does not say how the `Location` value is encoded, so a `?next=` value containing `%0d%0a` can still split the response after the target check passes.

**FAIL/PASS.** FAIL: `res.setHeader("Location", "/next?u=" + raw)` or a raw socket write with the header concatenated. PASS: the value is set through the framework's header API, the API rejects control characters, and a CR/LF reaching it returns 400 or is encoded rather than written.

1. https://www.rfc-editor.org/rfc/rfc9112.html (org: IETF). Section 11.1 explains why input filtering is not the fix: "A common defense against response splitting is to filter requests for data that looks like encoded CR and LF" (the page gives `%0D` and `%0A` as the encoded forms). It continues: "However, that assumes the application server is only performing URI decoding rather than more obscure data transformations..." Then the rule: "A more effective mitigation is to prevent anything other than the server's core protocol libraries from sending a CR or LF within the header section, which means restricting the output of header fields to APIs that filter for bad octets and not allowing application servers to write directly to the protocol stream." It also gives the redirect case: "a parameter within the request-target might be read by an application server and reused within a redirect, resulting in the same parameter being echoed in the Location header field of the response." Backs G5.
2. https://cwe.mitre.org/data/definitions/113.html (org: MITRE). The mitigation for CWE-113 is in the header-construction step: "Construct HTTP headers very carefully, avoiding the use of non-validated input data." It classifies the weakness as "Improper Neutralization of CRLF Sequences in HTTP Headers ('HTTP Request/Response Splitting')". Backs G5.
3. https://nodejs.org/api/http.html (org: OpenJS Foundation). The built-in API is the filter: in the `response.writeHead()` reference, "Attempting to set a header field name or value that contains invalid characters will result in a `TypeError` being thrown." That makes the header API the pass and a raw stream write the fail; the page documents `response.writeHead(statusCode[, statusMessage][, headers])` as the supported route for a whole header set. Backs G5.
4. https://docs.djangoproject.com/en/5.2/ref/request-response/ (org: Django Software Foundation). The same guarantee, with the exception named: "HTTP header fields cannot contain newlines. An attempt to set a header field containing a newline character (CR or LF) will raise `BadHeaderError`". Backs G5.

**Verdict.** 4 organisations for the whole rule (IETF, MITRE, OpenJS, Django). Per clause: "set headers through the API, never by concatenating onto the stream" has all four = 4; "reject or encode CR/LF at the boundary" has IETF, MITRE, Node and Django = 4. A clause about "validate the redirect target" already exists in `fn-redirect-target-allowlist`, so a new card should not repeat it. Confidence high.

## G6. Cookie scope: Domain, SameSite and the `__Host-` prefix

**Candidate Rule.** Set session cookies host-only (no `Domain`), use the `__Host-` prefix, and set an explicit `SameSite`.

**Level.** service. **Tool gate.** none found.

**Existing card.** `svc-session-lifecycle` (stable) already has `Secure`, `HttpOnly` and `SameSite` in its Rule, and `__Host-sid` in its PASS example, but not host-only scope or the prefix in the Rule. `svc-csrf-state-changing` (stable) already treats `SameSite` as defence in depth. Missing from the Rule: omit `Domain`, use `__Host-`, and the subdomain-injection reason.

**FAIL/PASS.** FAIL: `Set-Cookie: sid=...; Domain=example.com; SameSite=None` on an app that shares the domain with user content. PASS: `Set-Cookie: __Host-sid=...; Secure; HttpOnly; SameSite=Lax; Path=/` with no `Domain`.

1. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie (org: Mozilla). Omitting the attribute is the narrower default: "If omitted, the cookie is returned only to the host that sent it" — the page calls that a host-only cookie (paraphrase). The prefix buys the same at the browser: cookies with `__Host-` "must not have a `Domain` attribute specified, and the `Path` attribute must be set to `/`. This guarantees that such cookies are only sent to the host that set them, and not to any other host on the domain." Backs G6.
2. https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html (org: OWASP). "It is recommended to use a narrow or restricted scope for these two attributes. In this way, the `Domain` attribute should not be set (restricting the cookie just to the origin server)". The prefix is recommended for the session id: "`__Host-` — the cookie must be set with `Secure`, must not have a `Domain` attribute, and must use `Path=/`. Prevents subdomain forgery and HTTPS downgrade attacks. **Recommended for session IDs.**" The consequence of a broad domain: "Setting the `Domain` attribute to a too permissive value, such as `example.com` allows an attacker to launch attacks on the session IDs between different hosts and web applications belonging to the same domain". Backs G6.

**Verdict.** 2 organisations for the missing clause (Mozilla, OWASP). The attribute clause (Secure, HttpOnly, SameSite) already has five organisations behind the existing card (OWASP, Mozilla, NIST, Spring, Rails per its `borrowed_from`), so G6 is not an absent class: it is one clause — host-only scope and the `__Host-` prefix — short by one organisation. Confidence medium; do not create a card for it yet.

## Counter-evidence and limits

- RFC 9112 does not require rejecting a request with both framing fields; it says the combination "ought to be handled as an error" and then lets an intermediary strip `Content-Length` and forward. Microsoft does exactly that (strip, then close), while PortSwigger asks for rejection and AWS exposes a mode. A Rule that says only "reject" is stricter than the standard; "reject, or strip and close the connection" is the phrasing all four support.
- AWS's desync setting defaults to `defensive`, not `strictest`. The page fetched does not describe what each mode drops, so a check must not claim `strictest` is required, only that the attribute is not left at `monitor`.
- PortSwigger says HTTP/2 end to end is "inherently immune", but the same page says a downgrading front end reintroduces the class. "Use HTTP/2" is therefore not a passing check on its own; the check is that the downgrade path normalises and the backend rejects.
- For G2/G3 the vendors disagree about precedence between origin headers and CDN rules. Microsoft says Front Door "honors these header values and doesn't cache the responses, even if you override the caching behavior by using the Rules Engine", while Cloudflare says of Cache Deception Armor that "A `Cache-Control` header from the origin, or an Edge Cache TTL Cache Rule may override the protection." A reviewer must check the specific CDN, not assume origin headers win.
- Cloudflare's own docs make "don't trust GET bodies" necessary: it "caches contents of GET request bodies, but they are not included in the cache key". That is a vendor behaviour, not a general property; a card should state the invariant, not the vendor quirk.
- Cloudflare's Cache Deception Armor "depends upon Origin Cache Control", so enabling it is not sufficient; the origin's `Cache-Control` is still the load-bearing part.
- MITRE's CWE-444 mitigation list is not usable as a source: it offers "Terminate the client session after each request" and "Turn all pages to non-cacheable", both of which break the product, and names Apache as the strict parser. It is excluded as backing for G1 for that reason.
- MDN's `Domain` sentence ("This is more restrictive than setting the host name") is confusingly worded. OWASP states the recommendation more plainly, so a card should quote OWASP for the imperative and MDN for the browser rule.
- `svc-api-cache-control` and `svc-session-lifecycle` already own the load-bearing clauses of G3 and G6. A new card in either class risks repeating a stable Rule, which rule 8 forbids; extending the existing card is the cheaper path.

## Answer to "what is missing" per class

- G1: no card. A new `svc-request-framing` is well supported: IETF, PortSwigger, AWS, Microsoft and OpenJS back the rule, and four of them support the reject-or-close clause. Keep "no HTTP/1 downgrade" in Why or drop it, since only PortSwigger states it.
- G2: no card. A new `svc-cache-key-completeness` is supported by four organisations for the keying clause. Phrase "rewrite instead of excluding" as advice, not a Rule clause (one org).
- G3: `svc-api-cache-control` already owns `private`/`no-store`.
