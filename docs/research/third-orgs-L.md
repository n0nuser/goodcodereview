# Third-organisation sources for the L drafts (task L)

18 pages fetched and read. Every URL in the Rows section was opened; quotes are verbatim from the page. `lacks:` lines read from the cards on 2026-11-06. Pages in the UNFETCHED list were not opened, so no quote from them is used and none is counted.

## Rows

1. https://www.jetbrains.com/help/inspectopedia/LawOfDemeter.html (org: JetBrains). Rule page for inspection ID `LawOfDemeter`, so it documents the rule *and* a default: option `ignoreLibraryCalls` has "Default value: Selected". It states the rule as a practice: "The Law of Demeter is not really a law, but specifies a style guideline: never call a method on an object received from another call." Rationale: the code "is easier to maintain, adapt, and refactor, has less coupling between methods, less duplication, and better information hiding", and it prescribes the same shape as the card's PASS: "The above example might be better implemented as a method `payInvoice(Invoice invoice)` in `Customer`." The page also carries the counterpoint the card needs: "On the other hand, you may need to write many wrapper methods to meet this guideline." Backs **mod-law-of-demeter**.

2. https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/architectural-principles (org: Microsoft). Under "Don't repeat yourself (DRY)": "The application should avoid specifying behavior related to a particular concept in multiple places as this practice is a frequent source of errors." and "Make this construct the single authority over this behavior". Under "Single responsibility": objects "should have only one responsibility and that they should have only one reason to change". Both halves of the card's Rule. Note the page's own caveat, useful for the counterpoint: "Duplication is always preferable to coupling to the wrong abstraction." Backs **mod-no-shotgun-surgery**.

3. https://blog.ndepend.com/shotgun-surgery (org: NDepend). Names the smell and prescribes the fix: "Shotgun surgery happens when you have to make many changes in your codebase to achieve seemingly simple tasks." — "Knowledge should only exist in a single place in your codebase." — "Localizing changes should be a first class code maintenance goal." It also gives the reviewer's test the card asks for: "When you find yourself changing the same four files or classes for each simple change, such as the addition of a menu item, reconsider your design." Backs **mod-no-shotgun-surgery**. Not yet in `tools/orgs.py` (no `blog.ndepend.com` prefix); needs a mapping to count.

4. https://github.com/troessner/reek/blob/master/docs/Repeated-Conditional.md (org: the Reek project — **but see the warning below**). Documents a rule with a threshold and rationale: "Repeated Conditional is a case of Simulated Polymorphism. Basically it means you are checking the same value throughout a single class and take decisions based on this." and "If you get this warning then you are probably not using the right abstraction or even more probable, missing an additional abstraction." Default: `max_ifs` — "The maximum number of identical conditional tests permitted before Reek raises a warning. Defaults to 2." Backs **mod-no-repeated-switches**, first clause (detect the repeat). **Warning:** the repo owner is `troessner`, a person, and `PROMOTION.md` counts "the repository owner, not the host", so `tools/orgs.py` will record this as a person unless a project-level entry is added. Do not count it as an organisation without deciding that question.

5. https://kotlinlang.org/docs/sealed-classes.html (org: JetBrains; `kotlinlang.org` is already mapped to `jetbrains`). "All direct subclasses of a sealed class are known at compile time." The practice statement: "The key benefit of using sealed classes comes into play when you use them in a `when` expression. The `when` expression, used with a sealed class, allows the Kotlin compiler to check exhaustively that all possible cases are covered." Sealed classes are recommended where "Type-safe design is required … Particularly for state management or handling complex conditional logic." Backs **mod-no-repeated-switches** only partially: it backs "one closed hierarchy, one exhaustive place to handle each case", not "replace each copy of the switch with a polymorphic method". Confidence low.

6. https://refactoring.guru/inline-method (org: Refactoring.Guru). "When a method body is more obvious than the method itself, use this technique." — "Replace calls to the method with the method's content and delete the method itself." Why: "A method simply delegates to another method. In itself, this delegation is no problem. But when there are many such methods, they become a confusing tangle that's hard to sort through." Backs **fn-no-pass-through-wrapper** only partially: the page says a single delegation "is no problem" and targets methods whose body is "more obvious than the method itself", so it does not back deleting a forwarding method that names an intent. It also warns: "Make sure that the method isn't redefined in subclasses."

7. https://deviq.com/code-smells/middle-man/ (org: DevIQ / NimblePros). Closest match found to the card's FAIL example: the page's example is a `CustomerService` whose `GetById` is `public Customer GetById(int id) => _repository.GetById(id);`. Problem: "A class that only delegates forces callers to go through an extra layer without receiving any benefit in return." And the keep-list matches the card's "validate, adapt, or narrow": delegation is healthy when "A class adds behavior to the delegated calls (validation, caching, logging, orchestration)." Backs **fn-no-pass-through-wrapper**. Not in `tools/orgs.py` (`deviq.com` unmapped); needs a mapping to `nimblepros`.

8. https://raw.githubusercontent.com/pmd/pmd/main/pmd-java/src/main/resources/category/java/design.xml (org: PMD; `raw.githubusercontent.com` is not mapped, but the doc twin `docs.pmd-code.org` is, so cite the rendered rule page if a stable URL is needed). Rule `UselessOverridingMethod`: "The overriding method merely calls the same method defined in a superclass." with the example comment "`// why bother overriding?`". Backs **fn-no-pass-through-wrapper** narrowly: only the override-that-calls-super case, not a field that forwards to a collaborator, so it is a weaker third source than rows 6 and 7.

9. https://scipy.github.io/devdocs/dev/contributor/continuous_integration.html (org: SciPy). A real fail-the-job time bound with numbers: "Some CI jobs install `pytest-fail-slow` and report failures when the test execution time exceeds a threshold duration." — "By default, all tests are subject to a 5 second limit" (`--fail-slow=5.0` in the "full" job, `--fail-slow=1.0` in the "fast" job) — "Exceptions are made using the `pytest.mark.fail_slow` decorator". It also states the noise caveat the card needs: "Due to variation in execution times, tests with execution times near the threshold should be adjusted to avoid failure even if their execution time were to increase by 50%". Backs **code-test-suite-time-budget** for the per-test half only; it sets no suite-total budget. `scipy.github.io` is not in `tools/orgs.py`.

10. https://docs.pytest.org/en/stable/reference/reference.html#confval-testpaths (org: pytest project; `docs.pytest.org` already mapped). The `testpaths` setting: "Sets list of directories that should be searched for tests when no specific directories, files or test ids are given in the command line", and the rationale the card needs, verbatim: "Useful when all project tests are in a known location to speed up test collection and to avoid picking up undesired tests by accident." No default value is printed for this option (it is unset by default). Backs **py-test-collection-and-imports**, the `testpaths` clause; the `-X importtime` clause is not covered.

11. Same URL as row 8 (org: PMD), two more rules that back other cards. `DataClass`: "The lack of functionality may indicate that their behaviour is defined elsewhere, which is a sign of poor data-behaviour proximity." and "Refactoring a Data Class should focus on restoring a good data-behaviour proximity. In most cases, that means moving the operations defined on the data back into the class." `GodClass`: "God classes do too many things, are very big and overly complex. They should be split apart to be more object-oriented." `NcssCount` / `ExcessivePublicCount` give the size thresholds. Backs **mod-behaviour-lives-with-state** (row 11a) and **mod-cohesive-unit** (row 11b, the oversized-module clause).

12. https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-domain-model (org: Microsoft). "A domain entity in DDD must implement the domain logic or behavior related to the entity data" and "The entity's methods take care of the invariants and rules of the entity instead of having those rules spread across the application layer." Also: "A domain model entity implements behaviors through methods, that is, it's not an \"anemic\" model." It states the card's own limit as the counterpoint: "if your microservice or Bounded Context is very simple (a CRUD service), the anemic domain model in the form of entity objects with just data properties might be good enough". Backs **mod-behaviour-lives-with-state**.

13. https://deviq.com/domain-driven-design/anemic-model/ (org: DevIQ / NimblePros). "objects are said to be anemic if they have state but lack behavior", and "the objects that model the behavior of the problem space within the application should use encapsulation to manage their internal state and behavior". Its functional-programming note is a fair counterpoint: anemic models are "expected" in a functional design. Backs **mod-behaviour-lives-with-state**.

14. https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/enum (org: Microsoft). Direct guideline, verbatim: "DO use an enum to strongly type parameters, properties, and return values that represent sets of values." Also "DO favor using an enum instead of static constants." and the closed-set point the card's Why makes: "DO NOT use an enum for open sets". Backs **fn-no-stringly-typed-returns**.

15. https://mypy.readthedocs.io/en/stable/typed_dict.html (org: mypy project; already mapped). "TypedDict lets you give precise types for dictionaries that represent objects with a fixed schema", and of the uniform `dict[K, V]` alternative: "This is clearly not a good fit for `movie` above." Failure detection: "Mypy will detect an invalid key as an error". Backs **fn-known-keys-get-a-type**.

16. https://blog.logrocket.com/liskov-substitution-principle-lsp/ (org: LogRocket). The only fetched page that states the card's proxy as a practice: "To structure tests that follow the Liskov Substitution Principle: Write tests that validate the expected behavior of the superclass" and "Run those same tests against all subclasses". Backs **mod-subtype-passes-parent-tests**. Weak for rule 3: it is a paid-writer company blog whose LSP sections restate the principle, so a reviewer may call it a secondary summary. Also `blog.logrocket.com` is not in `tools/orgs.py`.

## Counter-evidence

- **fn-no-pass-through-wrapper** — https://refactoring.guru/inline-method: "In itself, this delegation is no problem." The page deletes a method only when "a method body is more obvious than the method itself", so it does not back a blanket "delete every forwarding method".
- **fn-no-anonymous-tuples** — https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/types/tuples (org: Microsoft). The page recommends the opposite of the card's Rule for return values: "Named elements make your code self-documenting without requiring a separate type definition", and "Instead of defining a class or using `out` parameters, return a tuple with named elements". Microsoft's criterion is lifetime and behaviour, not "fields differ in meaning": "Tuples work well for short-lived groupings where defining a class, struct, or record would add unnecessary ceremony. For long-lived domain concepts or types with behavior, prefer records, classes, or structs." Any card on this subject has to answer this page, not just out-source to it.
- **mod-subtype-passes-parent-tests** — https://khorikov.org/posts/2020-07-13-inheritance-in-unit-tests (person: Vladimir Khorikov; reference only, not an organisation). Of exactly the abstract-test-class pattern: "And still, I don't recommend that you do that." His reason is that the shared test class couples tests to the production base class.
- **mod-no-repeated-switches** — the Kotlin page (row 5) recommends one sealed hierarchy with one exhaustive `when`. That backs "one place covers every case", and it is compatible with the card, but read strictly it endorses keeping a type switch, which cuts against the card's "replace it with one polymorphic method".
