# Security pass: access control, injection, sessions, crypto, logging, LLM agents

Fetched 2026-10-24 through WebFetch (a small model summarises each page), so every row is a paraphrase of a summary, not of raw page text. OWASP and the IETF are the only publishers used. Each row gives the URL, the distilled point, whether a reviewer can mark it FAIL, and the card id it supports. Three URLs 404ed (OWASP's JWT cheat sheet under two names, the API Security 2023 index paths on `owasp.org`, which now redirect to `api-security.owasp.org`); the JWT row uses RFC 8725 instead.

## 1. Access control

1. https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html. Deny when no rule matches. Check on every request, server side, ideally through global config. Check the user's right to the specific object, not just the object type. Hidden or random IDs do not replace the ownership check. Enforce in more than one layer. Test deny-by-default and object-level access. FAIL: yes, a handler that loads by client ID with no owner check; a route with no policy. -> `fn-object-level-authz`, `svc-authz-central-deny-default`.
2. https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization. Every function that takes a client-supplied ID must check that the logged-in user may act on that record. GUIDs help but do not replace the check. Authorization tests gate deploys. FAIL: yes. -> `fn-object-level-authz`.
3. https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization. One auditable authorization module called from every business function. Deny unless a role is explicitly allowed. Admin controllers share a base class that checks the role. FAIL: yes, an admin route with no role check. -> `svc-authz-central-deny-default`.
4. https://top10.owasp.org/2025/A01_2025-Broken_Access_Control. Deny by default except public resources. Write access checks once and reuse them. Tie permissions to record ownership. Log access failures and alert on repeats. Keep stateless tokens short-lived. FAIL: yes for the first three. -> `svc-authz-central-deny-default`, `fn-object-level-authz`.
5. https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization. Do not copy client input into internal objects automatically. Reject writes to sensitive fields such as price, status or moderation flags. Return chosen fields, not whatever a generic serialiser emits, and validate responses against a schema. FAIL: yes. -> `fn-no-mass-assignment`, `fn-response-fields-explicit`.
6. https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html. Bind request data to a DTO that holds only the editable fields, or give binding an explicit allowlist. A blocklist alone fails when a field is added later. A DTO does not replace the authorization check. FAIL: yes. -> `fn-no-mass-assignment`.

## 2. Authentication and sessions

7. https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html. Prefer Argon2id (at least 19 MiB, 2 iterations, 1 lane), then scrypt, then bcrypt (legacy; 72-byte limit), then PBKDF2 (600,000 iterations with HMAC-SHA-256). Unique random salt per password. Plain SHA-256, MD5, SHA-1 and reversible encryption are out. Store algorithm and parameters with the hash and rehash at next login. FAIL: yes. -> `fn-password-slow-hash`.
8. https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html. Session cookies get `Secure`, `HttpOnly` and an explicit `SameSite`. Issue a new session ID at login and at privilege change, and invalidate the old one. Enforce idle and absolute timeouts on the server. Logout ends the session on the server. FAIL: yes. -> `svc-session-lifecycle`.
9. https://www.rfc-editor.org/rfc/rfc8725. JWT best current practice. The verifier takes an explicit list of accepted algorithms and rejects the rest. A key belongs to one algorithm, which blocks RSA-to-HMAC key confusion. Unsigned (`none`) tokens are not accepted unless the caller opts in. Check issuer, subject and audience. Do not trust `kid`, `jku` or `x5u` blindly. FAIL: yes. -> `fn-jwt-verify-pinned`.
10. https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html. Cap failed logins per account, not per IP. Return the same message, status and timing for unknown user, wrong password and locked account across login, recovery and registration. Lockout must not let an attacker lock out a victim for good. Do not use security questions. FAIL: yes. -> `svc-auth-throttle-generic-errors`.
11. https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption. Cap upload size, string length, array count and payload size. Validate any parameter that sets a record count. Set execution timeouts and per-client rate limits, tighter for OTP and password recovery. Cap batch size. Set spend limits on paid third-party calls. FAIL: yes. -> `svc-bound-client-controlled-sizes`, and the OTP point feeds `svc-auth-throttle-generic-errors`.

## 3. Injection, encoding and untrusted data

12. https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html. Encode for the output context (HTML body, attribute, JavaScript string, CSS value, URL). Avoid `innerHTML`, `outerHTML` and `document.write` with untrusted data; use `textContent`. Framework escape hatches such as `dangerouslySetInnerHTML` bypass built-in escaping. Sanitise user-authored HTML with a maintained library. CSP is defence in depth. FAIL: yes. -> `fn-no-raw-html-sink`.
13. https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html. Use a library call in place of a command when one exists. Never pass untrusted input to `sh -c`, `cmd.exe` or similar. Pass the program and each argument as separate list items, and still validate the arguments. Fix the executable and flags in code. Use `--` to end option parsing. FAIL: yes. -> `fn-no-shell-with-input`.
14. https://community.owasp.org/attacks/Path_Traversal. Avoid passing user input to file calls. Map a choice to a fixed ID instead of a file name. Normalise the path, then confirm it stays inside the intended directory. Watch for percent-encoded and double-encoded `../` and null bytes. Allowlist, do not strip. FAIL: yes. -> `fn-confine-file-path`.
15. https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html. `pickle.load(s)`, `yaml.load` with the full loader, `ObjectInputStream.readObject`, `BinaryFormatter`, `unserialize()` and typed JSON (`TypeNameHandling` other than `None`) on untrusted bytes can run code. Prefer data-only formats. Validating after deserialising is too late. Sign payloads and verify before reading. FAIL: yes, by grep. -> `fn-no-native-deserialise-untrusted`.
16. https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html. Allowlist extensions after decoding the name. The client Content-Type is untrusted. Cap size, counting decompressed size for archives. Replace the user's file name with a generated one. Store outside the web root or on another host, and serve through a handler. FAIL: yes. -> `svc-upload-validate-store`.
17. https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html. Validate on the server with allowlists per field type. Match the whole value with a regex, bound the length first, avoid backtracking-prone patterns and treat a match timeout as a failure. FAIL: yes for unbounded regex on request data. Mostly covered by the existing `mod-validate-at-boundary-once`; the regex point is not carded. -> `mod-validate-at-boundary-once` (existing, unchanged).

## 4. Browser-side controls

18. https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html. State changes need a synchroniser token or a signed double-submit token checked on the server. Naive double-submit is weak. `SameSite=Lax` still sends cookies on cross-site top-level GET, so it supports but does not replace the token. A GET that changes state defeats these defences. Reject simple content types on JSON APIs. Treat a missing or `null` Origin as untrusted. FAIL: yes. -> `svc-csrf-state-changing`.
19. https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html. Check the request Origin against a trusted list before echoing it back. Prefer named origins over `*`. CORS does not stop CSRF. The page does not cover `null` origin or `*` with credentials, so those points are not in the card. FAIL: yes for a reflected Origin. -> `svc-cors-allowlist`.
20. https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html. Send `Strict-Transport-Security`, `X-Content-Type-Options: nosniff` with accurate Content-Type, and CSP `frame-ancestors` (or `X-Frame-Options: DENY`). A CSP that blocks inline script matters for pages that render content. FAIL: yes, by header check. -> `svc-security-headers`.
21. https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Javascript_Management_Cheat_Sheet.html. Add Subresource Integrity hashes to vendor scripts, serve them with CORS, or mirror them in-house. A lapsed vendor domain can be re-registered. Not carded: one row, narrow to front-end repos; kept for a later pass. FAIL: yes. -> gap (no card).

## 5. Crypto, transport and data

22. https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html. Do not design algorithms. AES with GCM or CCM, or encrypt-then-MAC. Avoid ECB. Never reuse an IV under one key. Use a CSPRNG for keys, IVs, tokens and session IDs, never `rand()` or `Math.random()`. Keys come from a CSPRNG, live in a KMS or secrets manager, and are never in source. FAIL: yes. -> `fn-csprng-for-secrets`, `mod-vetted-crypto-only`.
23. https://top10.owasp.org/2025/A04_2025-Cryptographic_Failures. Use TLS 1.2 or newer with forward secrecy. Validate server certificates and the trust chain. Retire MD5, SHA-1, CBC and PKCS#1 v1.5. Classify data, keep sensitive data only as long as needed, discard early, tokenise or truncate when the full value is not needed, and send no-cache headers on sensitive responses. FAIL: yes. -> `fn-tls-verify-on`, `sys-pii-minimise-retention`.
24. https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html. TLS 1.3 by default, 1.2 only for compatibility; disable 1.0, 1.1, SSLv2 and SSLv3. A client must check the certificate chains to a trusted CA and matches the host. The page does not forbid disabling verification in code outright; the card rests on row 23 for that. FAIL: yes for old versions. -> `fn-tls-verify-on`.

## 6. Logging

25. https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html. Log authentication successes and failures, authorization failures, session failures, input validation failures and privileged actions, each with when, where, who and what plus a correlation ID. Never log passwords, session IDs, tokens, keys, connection strings or card data. Strip CR and LF from untrusted values, and prefer structured output. Make logs tamper-evident and access-controlled. FAIL: yes. -> `svc-security-event-logging`, and the never-log list overlaps existing `sys-secrets-and-errors`.
26. https://top10.owasp.org/2025/A09_2025-Security_Logging_and_Alerting_Failures. Log logins, access control events and validation failures with enough context; keep logs long enough to investigate; encode log data; keep tamper-resistant audit trails for transactions; alert on suspicious behaviour. FAIL: yes for a missing failure log. -> `svc-security-event-logging`.

## 7. LLM and agent code

27. https://genai.owasp.org/llmrisk/llm062025-excessive-agency/. Give the model only the tools it needs. Prefer narrow tools over open-ended ones (shell, generic URL fetch). Give downstream credentials the minimum scope, such as a read-only DB role. Act as the requesting user, not a shared admin identity. Require human approval for high-impact actions. Enforce authorization in the downstream system on every request. Log and rate-limit tool use. FAIL: yes. -> `sys-agent-tool-least-privilege`.
28. https://genai.owasp.org/llmrisk/llm052025-improper-output-handling/. Treat model output as untrusted. Encode it for its destination (HTML for pages, bound parameters for SQL) and restrict script execution with a strict CSP. FAIL: yes when model text reaches `innerHTML`, SQL or a shell. -> `fn-no-raw-html-sink`, `fn-no-shell-with-input`, existing `sys-prompt-injection`.
29. https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/. Limit input size, rate-limit per client, set timeouts, cap queues, log usage. FAIL: yes. -> `svc-bound-client-controlled-sizes` (size caps); rate and timeout parts already in `svc-rate-limit-quota` and `svc-timeouts`.
30. https://genai.owasp.org/llmrisk/llm032025-supply-chain/. Use only verifiable sources, scan and patch third-party components, keep a signed inventory, sign externally supplied code. Supports the existing supply-chain cards; no new rule.
31. https://arxiv.org/abs/2406.10279. Study of 16 code-generating models over 576,000 samples. At least about 5.2% of recommended packages were invented for commercial models and about 21.7% for open-source models. The authors call this a package confusion risk: an attacker can publish a malicious package under a name that models keep inventing. Peer-review status not checked. FAIL: yes, a dependency added in the diff that nobody checked in the registry. -> `chg-agent-grounded-code` (refined; no new card).

## 8. Not carded, with reasons

- NIST SSDF SP 800-218 (https://csrc.nist.gov/pubs/sp/800/218/final). The page names the framework but not the practice numbers, so no row maps to a rule. A later pass should read the PDF or the practice table.
- OWASP ASVS 5.0 chapter text and the CWE Top 25 list were not read in this pass. Rules above rest on the cheat sheets and Top 10 pages only.
- Input validation regex limits (row 17): already covered in spirit by `mod-validate-at-boundary-once`.
- Third-party script integrity (row 21): left as a gap.

## 9. Independent-org pass (2026-10-24)

Goal: lift each security card toward three orgs behind its Rule. OWASP ASVS, Cheat Sheets, Top 10, API Top 10 and the GenAI project count as one org. Every URL below was opened through WebFetch (small-model summary, so each row is a paraphrase). Rows give the URL, the distilled point, and the card whose Rule it backs. Where a page only backs part of a Rule, the row says which part.

JWT cheat sheet location: the OWASP sheet is now https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html (opened, 200). The old `JSON_Web_Token_for_Java_Cheat_Sheet.html` path returns 404. No card cited the dead path, so the new URL was added to `fn-jwt-verify-pinned`.

1. https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html. Hardcode the accepted signing algorithms; check `exp`, `iss` (and use only that issuer's keys) and `aud`; reject tokens missing required claims. -> `fn-jwt-verify-pinned`.
2. https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens. Web APIs validate the signature and issuer, and accept only tokens whose `aud` is their own identifier. -> `fn-jwt-verify-pinned` (signature, `iss`, `aud` parts; no algorithm-list clause).
3. https://developers.google.com/identity/gsi/web/guides/verify-google-id-token. Backend checks signature, `aud`, `iss` and `exp`; use a library rather than hand-rolled code. -> `fn-jwt-verify-pinned`.
4. https://codeql.github.com/codeql-query-help/javascript/js-jwt-missing-verification/. Calling verify with no key selects the `none` algorithm and drops integrity checks (CWE-347). -> `fn-jwt-verify-pinned`.
5. https://docs.python.org/3/library/secrets.html. Use `secrets`, not `random`, for tokens and passwords; `random` is for simulation. -> `fn-csprng-for-secrets`.
6. https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/random. `Math.random()` is not cryptographically secure; use `crypto.getRandomValues()`. -> `fn-csprng-for-secrets`.
7. https://www.rfc-editor.org/rfc/rfc4086.html. Pseudo-random processes used for secrets give "pseudo-security"; an attacker can search a small set of outcomes. -> `fn-csprng-for-secrets`.
8. https://pkg.go.dev/crypto/rand. Go's `crypto/rand` is the CSPRNG, with a `Text` helper intended for secrets and tokens. -> `fn-csprng-for-secrets`.
9. https://go.dev/blog/osroot. Sanitising a path string misses symlinks and check-then-use races; `os.Root` / `os.OpenInRoot` refuse any escape from the root. -> `fn-confine-file-path`.
10. https://codeql.github.com/codeql-query-help/python/py-path-injection/. Normalise (`realpath`), then confirm the result starts with a safe root; CWE-22. -> `fn-confine-file-path`.
11. https://learn.microsoft.com/en-us/aspnet/core/data/ef-mvc/crud?view=aspnetcore-9.0. Bind an explicit property list or a view model so fields added later stay protected. -> `fn-no-mass-assignment`.
12. https://guides.rubyonrails.org/action_controller_overview.html. Strong Parameters block mass assignment until attributes are permitted; `permit!` is flagged as risky. -> `fn-no-mass-assignment`.
13. https://docs.djangoproject.com/en/5.2/topics/forms/modelforms/. Set `fields` explicitly; `__all__` and `exclude` are called much less secure and tied to serious exploits. -> `fn-no-mass-assignment`.
14. https://docs.python.org/3/library/pickle.html. Unpickling untrusted data can run arbitrary code; use a format such as JSON. -> `fn-no-native-deserialise-untrusted`.
15. https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide. `BinaryFormatter` cannot be made safe; prefer `System.Text.Json` or XML serializers; data crosses trust boundaries more often than authors expect. -> `fn-no-native-deserialise-untrusted`.
16. https://docs.oracle.com/en/java/javase/21/core/serialization-filtering1.html. Deserialising untrusted data is an attack; stream filters (allow/reject lists) screen classes first. -> `fn-no-native-deserialise-untrusted` (note: Java treats a filter as a mitigation, so "never" in the Rule is stricter than this page).
17. https://codeql.github.com/codeql-query-help/python/py-unsafe-deserialization/. Avoid deserialising untrusted data; use JSON or `yaml.safe_load` (CWE-502). -> `fn-no-native-deserialise-untrusted`.
18. https://developer.mozilla.org/en-US/docs/Web/API/Element/innerHTML. Use `textContent` for plain text; if HTML is needed, sanitise through a Trusted Types policy. -> `fn-no-raw-html-sink`.
19. https://web.dev/articles/trusted-types. Trusted Types lock `innerHTML` and similar sinks; build nodes with `createElement` / `textContent`. -> `fn-no-raw-html-sink`.
20. https://react.dev/reference/react-dom/components/common. `dangerouslySetInnerHTML` runs any markup; use only with trusted, sanitised data. -> `fn-no-raw-html-sink`.
21. https://www.cisa.gov/resources-tools/resources/secure-design-alert-eliminating-cross-site-scripting-vulnerabilities. Use frameworks with built-in output encoding; escape by hand otherwise; sanitisation alone is not infallible. -> `fn-no-raw-html-sink`.
