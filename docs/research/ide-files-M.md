# Task M: committed IDE and per-user files

Read on 2026-11-06. Claims checked:

- **M-a** — do not commit files that hold one developer's editor/IDE state or the operating system's metadata.
- **M-b** — list those paths in `.gitignore`, or in the machine-wide excludes file when the path exists only on one machine.
- **M-c** — keep the settings the team shares in the repository.

Quote marks are verbatim from the fetched page. Where the page lists paths rather than prose, the listed lines are quoted.

## Counter-evidence

- **Apple does not state the Xcode part of the claim.** Apple's fetched pages document the opposite design in one place: the Xcode 4 Transition Guide has a section "Save Internal Project Files in Repositories" and says "In Xcode 4.1 and later, you can use repositories to view internal project files (schemes, user interface settings, and so forth) when looking at SCM details in the SCM commit and update workflows." Apple also only requires *shared* schemes for Xcode Cloud; it never says to ignore `xcuserdata`. So `xcuserdata/` and `*.xcuserstate` are backed by GitHub's template only (row 5). Keep them as examples, not as a clause, or the Xcode clause fails the three-organisation floor.
  - https://developer.apple.com/library/archive/documentation/IDEs/Conceptual/Xcode4TransitionGuide/SCM/SCM.html (org: Apple).
- **A blanket `.idea/` ignore is wrong, by JetBrains' own guidance.** JetBrains says to share "All files under the `.idea` directory … **except**" three user-specific items (row 9). GitHub's JetBrains template likewise ignores only user-specific paths (row 4). The card must list the user files, not the directory.
- **`.vscode/settings.json` is not inherently personal.** Microsoft says workspace settings in `.vscode` are there "to share settings with others" and are "shared by all users of that project" (row 11); GitHub's VS Code template keeps `settings.json` and ignores the rest (row 8). A rule that tells teams to ignore `.vscode/` or `.vscode/settings.json` wholesale contradicts both. Only personal `.vscode` state (history, caches, absolute paths) belongs in the ignore file.
- **The shared `.gitignore` is optional for one-machine files.** GitHub explicitly offers `.git/info/exclude` for "files created by your editor" that other users will not generate, and Git says editor files go in `core.excludesFile` (rows 1, 2). A FAIL should accept either the repo ignore file or the machine-wide excludes, not demand a repo-level entry for a path only one developer has.
- **`.DS_Store` and `Thumbs.db` have two organisations, not three.** Only GitHub's templates (rows 6, 7) and alint (row 15) name them; Microsoft and Git speak about "temporary files" generally. Keep them as examples under the general clause.
- **A single workspace file cannot always separate shared and personal settings.** VS Code's design has one `.vscode/settings.json` for the workspace; a team that wants project settings there must sometimes commit a file containing a personal-looking value. This is an argument for reviewing the content, not for a blanket ignore.

## Candidate card

- **Level:** change.
- **Severity:** should-fix (draft cap; the sources do not justify `block`).
- **Existing card:** none. `rg -n -i 'gitignore|xcuserdata|DS_Store|Thumbs\.db|\.idea/|workspace\.xml' cards packs` finds only a comment in `packs/go/go-mod-readonly-verified.md`. `chg-author-hygiene` is adjacent (it mentions "stray debug lines" and a red build) but does not cover ignore files or IDE state. No duplicate.

**Rule.** Do not commit a file that holds one developer's editor or IDE state (the `xcuserdata/` directory and the `*.xcuserstate` files inside it, `.idea/workspace.xml`, and the other per-user files the IDE documents, such as `.idea/usage.statistics.xml` and `.idea/shelf/`) or the operating system's metadata (`.DS_Store`, `Thumbs.db`). List those paths in `.gitignore`, or in the machine-wide excludes file when the path exists only on one machine. Keep the settings the team shares (`.idea/codeStyles/`, `.vscode/settings.json`, `xcshareddata/xcschemes/`) in the repository.

The two named files with only two organisations (`.idea/usage.statistics.xml`/`.idea/shelf/`, `.DS_Store`/`Thumbs.db`) and the one with one (`xcuserdata/`) are examples inside the general clause. If the maintainer reads each enumerated path as its own clause, cut them back to the general wording and move the names to the Why.

**Why.** Per-user state changes on every IDE session and every machine, so it adds diff noise and merge conflicts. The shared files are the ones a teammate or CI needs.

**FAIL.** The diff adds `.idea/workspace.xml` and `xcuserdata/alice.xcuserdatad/xcschemes/App.xcscheme`, and no `.gitignore` or global exclude covers either path.

**PASS.** The diff adds `.gitignore` entries for `.idea/workspace.xml`, `.idea/shelf/`, `xcuserdata/`, `*.xcuserstate`, and `.DS_Store` (or those paths are in the machine-wide excludes), and commits only `.idea/codeStyles/Project.xml`, `.vscode/settings.json`, and `App.xcodeproj/xcshareddata/xcschemes/App.xcscheme`.

**Counterpoint.** Teams that standardise on one IDE rely on committed run configurations and schemes, and a blanket ignore throws those away. Answer: those live in shared locations — `.idea/runConfigurations/`, `xcshareddata/xcschemes/`, `.vscode/launch.json` — not in `workspace.xml` or `xcuserdata`; commit the shared location and ignore the per-user one. A one-developer repository can keep the paths in the global excludes instead of the shared `.gitignore`.

**Tool gate.** alint's bundled `hygiene-no-macos-junk` and `hygiene-no-windows-junk` rules (level `error`) catch committed `.DS_Store` / `Thumbs.db`. No shipped rule catches IDE state by name: `hygiene-no-editor-backups` mentions `.idea/workspace.xml` in its explanation but its shipped paths are only `*~`, `*.swp`, `*.swo`, `*.bak`, `*.orig`, so it will not fire on a committed `workspace.xml`. For the IDE paths, configure alint's `git_no_denied_paths` rule with a `denied` list (`xcuserdata/**`, `*.xcuserstate`, `.idea/workspace.xml`, `.idea/usage.statistics.xml`, `.idea/shelf/**`, `.DS_Store`, `Thumbs.db`). The rule exists and is documented, but it is a rule kind that needs configuration; if `tool_gate` must name a shipped rule, use the two junk rules and leave the IDE paths to review.
