# Three test-suite practices (N1-N3): organisation sources

Fetched 2026-11-06. Every row below is a page I fetched and read; wording in quote marks is verbatim from the fetched page, rows without quote marks are paraphrase. I count organisations, not pages. `docs/PROMOTION.md` rules 1 to 3 apply.

The three candidate claims:

- **N1**: unit tests stay off the network, the real filesystem, the database and the real clock; those dependencies belong to a separate, slower tier.
- **N2**: when tests run in parallel, each worker gets its own database; no two workers share a mutable one.
- **N3**: a pull request runs only the tests affected by the change, with a full-suite run outside the pull-request gate.

## Cards that already cover part of this

- **N1**: `packs/python/py-test-hygiene.md` (stable, module, Python) already has the Rule "Freeze time and block network in tests." It cites only the author's own guide. It does not cover the real filesystem, the database, or the separate tier, and it is Python/module rather than codebase. A new codebase card would repeat part of its Rule; under rule 8 the two must be merged or the weaker one deleted. This is the main promotion risk for N1.
- **N2**: `packs/python/py-xdist-worker-isolated-state.md` (stable, module, Python) already has the Rule "Under pytest-xdist, give each worker its own database or other mutable resource, keyed by `worker_id`...". That is N2 for pytest. `cards/audit/codebase/code-test-fixtures-built-once.md` (stable) also says "give each parallel worker its own database" in its Counterpoint, but that is not its Rule. A new language-neutral N2 card would duplicate the stable Python card's Rule for its main audience; treat N2 as a scope expansion of an existing card, not a new card, unless the parent merges the two.
- **N3**: no card covers test impact analysis or affected-test selection. `cards/audit/codebase/code-test-suite-time-budget.md` is a draft about a time budget and failing a build on duration, not about selecting tests. `cards/change/chg-tests-ship-with-change.md`, `code-flaky-test-quarantine` and `code-test-fixtures-built-once` are about other test practices. N3 has no duplicate.

## Candidate cards

### N1

- **Rule**: Unit tests do not touch external I/O (the network, the real filesystem, or the database) or the real clock; a dependency that needs them is replaced with a double, or the test moves to a separate, slower integration tier.
- **Level**: `codebase`.
- **Tool gate**: `pytest-socket --disable-socket` where pytest is used, plus a unit-test CI job with no database service and no network credentials.
- **FAIL one-liner**: A test in the unit tier calls `requests.get("https://api.example.com")`, reads a repository path, or asserts on `datetime.now()`, and the only CI job runs that tier together with everything else.
- **PASS one-liner**: The unit job runs with sockets disabled, a temporary directory or in-memory filesystem, an injected fixed clock and no database; a separate integration job exercises the real service and clock.
- **Do not write the Rule as "no network and no filesystem" as two separate clauses**: network alone has Google and GitLab (2 orgs) and filesystem alone has Google and Microsoft (2). The broad clause "external I/O (network, filesystem or database)" has six. The clock clause has three.

### N2

- **Rule**: When the test suite runs in parallel, each worker gets its own database created from the same schema; no two workers share a mutable database.
- **Level**: `codebase`.
- **Tool gate**: none. Django `--parallel`, Rails `parallelize`, Laravel `--parallel` and pytest-xdist `-n` are mechanisms, not rules with a threshold.
- **FAIL one-liner**: `pytest -n auto` starts every worker against the same `test_db`, or `manage.py test --parallel` points at one external test database that all workers mutate.
- **PASS one-liner**: Django `--parallel`, Rails `parallelize`, Laravel `--parallel`, or a `worker_id`-suffixed database per worker, all created from the same schema.
- **Do not write "database, schema or transaction"**: the four sources below say database per worker. None states a per-worker schema or a per-worker transaction as the default. A "schema" clause has no source here.

### N3

- **Rule**: On a pull request, run only the tests affected by the change; keep a full-suite run outside the pull-request gate, before deploy or on a schedule.
- **Level**: `codebase`.
- **Tool gate**: a PR job that runs the affected-tests command (`nx affected -t test`, Azure Test Impact Analysis, Develocity Predictive Test Selection) and a full-suite job off the PR path.
- **FAIL one-liner**: The pull-request workflow runs `pytest`/`npm test` over the whole repository, and there is no nightly, post-merge or pre-deploy full run.
- **PASS one-liner**: The pull request runs `nx affected -t test` (or Azure TIA), and a nightly or post-merge job runs the remaining/full suite.
- **Do not write "before merge"**: I found no source that says the full suite must run before merge. The three sources for the full-run clause say before deploy (Meta, Shopify) or at a configured periodicity (Microsoft). If the card says "before merge", that arm has 0 organisations.

## N1 sources

1. https://abseil.io/resources/swe-book/html/ch11.html (org: Google). Google classifies tests by size and enforces the small-test restrictions: "small tests aren't allowed to access the network or disk", and "they aren't allowed to sleep, perform I/O operations, or make any other blocking calls." The prescribed replacement is a double: "Testing code that relies on these sorts of operations requires the use of test doubles ... to replace the heavyweight dependency with a lightweight, in-process dependency." The larger tests are kept out of the developer loop: "Teams at Google will frequently isolate their large tests from their small or medium tests, running them only during the build and release process so as not to impact developer workflow." Also names the clock as a source of nondeterminism: "Software provides many sources of nondeterminism: clock time, thread scheduling, network latency, and more." Backs N1 (network, disk, tier; clock in the Why).
2. https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices (org: Microsoft). A good unit test is "Isolated": "Unit tests are standalone, can run in isolation, and have no dependencies on any outside factors, such as a file system or database." It is also "Fast": "Unit tests should take little time to run. Milliseconds." The split is explicit: "The dependencies make the tests slow and brittle and should be reserved for integration tests", and "You can also keep your unit tests in a separate project from your integration tests." For the clock, the page says "One principle of a unit test is that it must have full control of the system under test. However, this principle can be problematic when production code includes calls to static references (for example, `DateTime.Now`)." It then shows an `IDateTimeProvider` seam and a stub. Backs N1 (filesystem, database, clock, tier).
3. https://docs.spring.io/spring-framework/reference/testing/unit.html (org: Spring). Service-layer unit tests can be written "by stubbing or mocking DAO or repository interfaces, without needing to access persistent data while running unit tests." "True unit tests typically run extremely quickly, as there is no runtime infrastructure to set up." Backs N1 (database; the "no runtime infrastructure" rationale, not the network or filesystem).
4. https://docs.gitlab.com/development/testing_guide/testing_levels/ (org: GitLab). Under unit tests: "These tests should be isolated as much as possible. For example, model methods that don't do anything with the database shouldn't need a DB record. Classes that don't need database records should use stubs/doubles as much as possible." For frontend unit tests: "All server requests: When running frontend unit tests, the backend may not be reachable, so all outgoing requests need to be mocked." For the clock: "The behavior depends on polling or another timer interval. Unit and component tests use fake timers, so the test can advance time instead of waiting." The tiering is explicit: "Most of our tests should be at the unit level, with fewer tests as we move up each layer. End-to-end tests at the top are the most expensive to run and maintain." Backs N1 (network, clock, tier); its database remark is conditional, so it does not back the database clause on its own.
5. https://docs.djangoproject.com/en/5.1/topics/testing/tools/ (org: Django Software Foundation). "`SimpleTestCase` disallows database queries by default. This helps to avoid executing write queries which will affect other tests since each `SimpleTestCase` test isn't run in a transaction." Tests that need the database move to `TestCase`/`TransactionTestCase`. Backs N1 (database).
6. https://guides.rubyonrails.org/testing.html (org: Rails / Ruby on Rails project). Rails gives `travel_to` for time-sensitive code: "Inside the `travel_to` block `Date.current` is stubbed". System tests are a separate, slower tier: "If you are using System Tests, `bin/rails test` will not run them, since they can be slow. To also run them, add another CI step that runs `bin/rails test:system`". Backs N1 (clock, tier).
7. https://laravel.com/docs/12.x/testing (org: Laravel). 'Tests within your "Unit" test directory do not boot your Laravel application and therefore are unable to access your application's database or other framework services.' Feature tests are the larger tier. This page also carries the main counterpoint, below: "Generally, most of your tests should be feature tests." Backs N1 (database, tier) and is counter-evidence to a unit-majority reading.

## N2 sources

8. https://docs.djangoproject.com/en/5.1/topics/testing/advanced/ (org: Django Software Foundation). `--parallel` "specifies the number of processes. If `parallel` is greater than `1`, the test suite will run in `parallel` processes. ... Each process gets its own database." For classes that cannot run in parallel, `SerializeMixin` runs them sequentially with a filesystem lockfile. Backs N2.
9. https://guides.rubyonrails.org/testing.html (org: Rails / Ruby on Rails project). "When parallelizing tests, Active Record automatically handles creating a database and loading the schema into the database for each process. The databases will be suffixed with the number corresponding to the worker. For example, if you have 2 workers the tests will create `test-database-0` and `test-database-1` respectively." Backs N2.
10. https://laravel.com/docs/12.x/testing#running-tests-in-parallel (org: Laravel). "Laravel automatically handles creating and migrating a test database for each parallel process that is running your tests. The test databases will be suffixed with a process token which is unique per process. For example, if you have two parallel test processes, Laravel will create and use `your_db_test_1` and `your_db_test_2` test databases." Backs N2.
11. https://pytest-django.readthedocs.io/en/latest/database.html (org: pytest-django / pytest-dev). "By default, each xdist process gets its own database to run tests on. This is needed to have transactional tests that do not interfere with each other." The docs also show how to override this to use one database, which is the FAIL. Backs N2.

## N3 sources

12. https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/ (org: Meta). Predictive test selection "needs to run only a small subset of tests in order to reliably detect faulty changes." Meta reports it catches "more than 99.9 percent of all regressions before they are visible to other engineers in the trunk code, while running just a third of all tests that transitively depend on modified code." For the full-run arm, Meta says "Every code change undergoes exhaustive testing before it is deployed from the trunk to production" (before deploy, not before merge). Backs N3 (selection; full run before deploy).
13. https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops (org: Microsoft). TIA "automatically selects only the subset of tests required to validate the code being committed." The selection "includes existing impacted tests, previously failing tests, and newly added tests." Two clauses matter for the card: "For commits and scenarios that TIA can't understand, it falls back to running all tests", and "Configurable overrides. You can run all tests at a configured periodicity. ... Setting this option is recommended". The same page says TIA is not supported for .NET Core, which is a real limitation. Backs N3 (selection, safe fallback, scheduled full run).
14. https://shopify.engineering/spark-joy-by-running-fewer-tests (org: Shopify). On a 150,000-test suite that took 30-40 minutes, "it became apparent that the right solution was to only run the tests related to the code change." The selected run averages about 60% of tests, and recall was 99.94%. The full suite remains: "we run the full test suite every deploy", and "The full test suite runs asynchronously. Pull requests can get merged before the full test suite completes." Backs N3 (selection; full run before deploy).
15. https://abseil.io/resources/swe-book/html/ch23.html (org: Google). On presubmit, "we typically limit presubmit tests to just those for the project where the change is happening." After submit, "we use TAP to asynchronously run all potentially affected tests, including larger and slower tests." Also "After a change is submitted, the CB should run all relevant tests." Google selects a subset on presubmit and moves the rest to post-submit; it does not say the post-submit run is the entire suite. Backs N3 (subset on PR, rest outside the PR) but not the full-suite clause.
16. https://nx.dev/ci/features/affected (org: Nx). "Most pull requests change a few files, so CI should only run the tasks those files affect. `nx affected` selects and runs only the tasks that need to run for the given changes." The page explains the base/head commits for CI but says nothing about a full-suite run. Backs N3 (selection only).
17. https://develocity.ai/product/predictive-test-selection/ (org: Gradle / Develocity; vendor documentation for its own product). "Predictive Test Selection runs only the tests relevant to a change and skips the rest — recording why every test was selected or skipped." It always runs "Recently failed or flaky tests ... regardless of selection score; the model errs toward selection when uncertain." The page does not mention a full-suite fallback or schedule. Backs N3 (selection only; vendor feature page, so weaker than the team posts).
18. https://docs.develocity.ai/current/using-develocity/predictive-test-selection/ (org: Gradle / Develocity; vendor documentation for its own product). The docs split the run across pipeline stages: "You trade full test coverage for faster feedback: local and pre-merge builds complete faster, while a subsequent pipeline stage can run the remaining tests." The two modes are explicit: "Relevant tests mode selects the most relevant subset for the current changeset. Use this for pre-merge CI jobs and local pre-commit checks to get fast feedback." "Remaining tests mode selects the tests that were not run in a prior relevant-tests execution against the same changeset. Use this for post-merge or nightly builds to ensure complete coverage." Pairing them means "each test runs at most once per changeset." Backs N3 (selection on pre-merge, complete coverage post-merge/nightly). Vendor docs, so weaker than the Meta/Microsoft/Shopify posts.

## Counter-evidence

- **N1, Laravel recommends the opposite balance**: Laravel's page says Unit tests cannot reach the database or framework services, then says "Generally, most of your tests should be feature tests. These types of tests provide the most confidence that your system as a whole is functioning as intended." That is a real objection to making the isolated unit tier the majority; the card should say what the unit tier must not touch, not that most tests must be unit tests.
- **N1, Google keeps real dependencies where it can**: Google's chapter says it prefers not to over-mock: "at Google, we prefer to keep the real dependencies in place when it is feasible to do so." The card's doubles are for the network/disk/database/clock boundary, not for every collaborator. Do not let the card become "mock everything".
- **N1, Spring's page does not mention the network or filesystem**: Spring backs only "no persistent data" and "no runtime infrastructure". It cannot be counted for the network or filesystem clause on its own.
- **N2, Go has no per-worker database**: Go's `testing` docs describe `t.Parallel()` as a signal "that this test is to be run in parallel with (and only with) other parallel tests"; the tests share one process. There is no worker database and no built-in isolation. The N2 Rule therefore needs a DB-backed runner (Django, Rails, Laravel, pytest-django) or an explicit per-test database in Go. The existing Python card has the same scope limit.
- **N2, not every test can be parallelised**: Django ships `SerializeMixin` exactly because some classes "share a common resource" and must run sequentially. A card that says "parallelise everything" is wrong; it should say "when parallel, isolate the database".
- **N3, selection misses regressions**: Shopify says "The generated mapping from dynamic analysis can get out of date with the latest main, and sometimes failing tests won't get selected and get merged to main." It measures about 0.06% of pull requests with failing tests merged, and runs the full suite asynchronously to catch them. Microsoft has a safe fallback for unknown file types; TIA is not supported for .NET Core. A card must keep the full run and a fallback, or the FAIL is real.
- **N3, "before merge" is not sourced**: Meta says exhaustive testing before deploy; Shopify says the full suite runs every deploy and PRs can merge before it finishes; Microsoft says a configured periodicity. None says the full suite blocks the merge. If the parent wants "before merge", the card fails rule 1.
- **N3, tool vendor pages are not team practice**: Nx and Gradle document selection features, not a team describing what it does and why. They count only as tool docs; if vendor docs are excluded, selection still has Meta, Microsoft and Shopify (3).

## Also read, no rule

- https://turborepo.com/docs/crafting-your-repository/running-tasks (org: Turborepo). Shows source-control filters, e.g. `turbo build --filter=[main...my-feature]`, and says "Using filters to run tasks based on changes in source control is a great way to run tasks only for the packages that are affected by your changes." It is a feature guide, not a rule that PRs must select tests or that a full run must happen; no rule.
- https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html (org: Google). Recommends a 70/20/10 unit/integration/end-to-end split. It supports the separate-tier Why for N1 but does not state the network/filesystem/clock isolation; same organisation as the Google chapter, so it adds no organisation. No separate rule.
- https://research.google/pubs/taming-google-scale-continuous-testing/ (org: Google). A research abstract about TAP and test workload; it describes a project and results, not a practice a reviewer can mark FAIL. Excluded from counts.
- https://pypi.org/project/pytest-socket/ (project: pytest-socket; one maintainer). Documents "Run `pytest --disable-socket`, tests should fail on any access to `socket` or libraries using socket with a `SocketBlockedError`." This is the N1 tool gate. The maintainer is a person, not an organisation, so it does not count toward the three; the package page is still the mechanism to name in `tool_gate`.
- https://docs.djangoproject.com/en/5.1/topics/testing/advanced/ (org: Django). `SerializeMixin` is the documented way to run resource-sharing classes sequentially; used as counter-evidence for N2, not as a rule for N2.

## Counts

- **N1, network/filesystem/database as one "external I/O" clause**: Google, Microsoft, Spring, GitLab, Django, Laravel = 6 organisations. If split: network has Google and GitLab (2); filesystem has Google and Microsoft (2); database has Microsoft, Spring, Django, Laravel (4). High confidence only for the broad "external I/O" wording.
- **N1, clock**: Microsoft, GitLab, Rails = 3. High confidence. Google mentions clock as a source of nondeterminism but does not prescribe freezing it, so it is not counted here.
- **N1, separate slower tier**: Google, Microsoft, GitLab, Rails = 4. High confidence. Laravel also separates Unit and Feature, but its "most tests should be feature" line conflicts with the unit-majority reading, so it is listed under Counter-evidence rather than counted here.
- **N2, per-worker database**: Django, Rails, Laravel, pytest-django = 4. High confidence; all four state it as the default or the documented parallel setup. No source for a per-worker schema or transaction.
- **N3, affected-test selection on a pull request**: Meta, Microsoft and Shopify are three team-practice sources; Nx and Gradle (two pages, one organisation) are tool docs for selection features, so counting them gives five. Add Google as a sixth only for the weaker "a subset on presubmit" (Google selects by project, not by affected files). High confidence for the three, medium-high for five.
- **N3, full suite outside the PR gate**: Microsoft (configured periodicity), Shopify (every deploy), Meta (exhaustive before deploy), Gradle (remaining tests post-merge or nightly) = 4, or 3 without vendor docs. Medium-high confidence. "Before merge" = 0; Google's post-submit run is "all potentially affected", not the full suite.

## Doubts for the parent

- **N1 is the strongest new card, but rule 8 collides with `py-test-hygiene`.** The stable Python card already says "Freeze time and block network in tests." A new `codebase` card must either merge that card into itself or be framed as the language-neutral parent of it. If the parent will not delete or rewrite `py-test-hygiene`, N1 should not be promoted as a separate card.
- **N2 should probably not be a new card.** `py-xdist-worker-isolated-state` is stable and already says the whole Rule for pytest. A codebase card would add Django/Rails/Laravel examples but repeat the Rule, which rule 8 rejects. The better move is a scope expansion or a cross-language card that explicitly supersedes the Python one.
- **N3 is the cleanest new card, but the "full run" clause must be worded as "before deploy or on a schedule".** Writing "before merge" loses the third organisation and makes the card fail rule 1. The card should also keep Microsoft's safe fallback and Shopify's "PR can merge before the full run" caveat in the Counterpoint, not the Rule.
- **`tools/orgs.py` gaps**: `develocity.ai` (Gradle) is not mapped; a card citing the Gradle page would fail validation until the prefix is added. `turborepo.com` is also unmapped. `nx.dev`, `pytest-django`, `docs.djangoproject.com`, `guides.rubyonrails.org`, `laravel.com`, `docs.spring.io`, `abseil.io`, `engineering.fb.com`, `shopify.engineering`, `learn.microsoft.com` and `docs.gitlab.com` are already mapped.
