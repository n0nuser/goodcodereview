# Test-suite speed, Python-specific practices: sources

Fetched 2026-11-05 through WebFetch. Rows in quote marks are verbatim from the fetched page; rows without quote marks are paraphrase. `docs.pytest.org`, `docs.python.org`, and `github.com/zupo/awesome-pytest-speedup` were excluded by the brief and are not repeated here.

## C1. pytest-xdist: session fixtures run once per worker; one database per worker

1. https://pytest-xdist.readthedocs.io/en/stable/how-to.html (org: pytest-xdist project). Each worker collects and runs its own subset, so a session-scoped fixture is built once per worker: "each worker process will perform its own collection and execute a subset of all tests", and "tests in different processes requesting a high-level scoped fixture (for example `session`) will execute the fixture code more than once". The page's answer for an expensive fixture is a shared lock file so the data is produced once: the fixture is expensive, "because it is resource intensive", and the recipe is also for "initializing a database service and populating initial tables". Backs C1.
2. https://pytest-django.readthedocs.io/en/latest/database.html (org: pytest-django project). Under "Use the same database for all xdist processes" it states the default: "By default, each xdist process gets its own database to run tests on. This is needed to have transactional tests that do not interfere with each other." Backs C1.
3. https://blog.trailofbits.com/2025/05/01/making-pypis-test-suite-81-faster/ (org: Trail of Bits, for PyPI/Warehouse). Moving to `--numprocesses=auto` "immediately" exposed that "Each test worker needed its isolated database instance to prevent cross-test contamination"; their fixture changed to `pg_db = f"tests-{worker_id}"`. Measured result: "Test execution time 191s → 63s, 67% reduction". Overall "reducing execution time from 163 seconds to 30 seconds while the test count grew from 3,900 to over 4,700". Backs C1.
4. https://exante.eu/press/blog/2925-how-we-made-python-pytest-suites-8-5x-faster/ (org: EXANTE). Parallelising with pytest-xdist was "The First Big Win"; they needed `--dist=loadfile` so a file's tests share a worker, then split monolithic test files because "Some files had dozens of quick tests; others had only a couple of heavy scenarios" and workers sat idle. Average suite went from 20-25 minutes to about two minutes, "an 88% reduction" and "8.5×" faster. Backs C1.

## C2. pytest-django `--reuse-db` / `--create-db`; Django `TestCase` rollback and `setUpTestData`

5. https://pytest-django.readthedocs.io/en/latest/database.html (org: pytest-django project). `--reuse-db` "will allow much faster startup time for tests", and "This can be especially useful when running a few tests, when there are a lot of database tables to set up"; `--create-db` "will re-create the database, regardless of whether it exists or not" and is needed after schema changes. The default setup "caches" the database and "rolls back transactions, to isolate tests from each other", and `--no-migrations` "may be faster when there are several migrations to run in the database setup". Their transaction-testing section says `TransactionTestCase`-style tests "are much slower to set up due to the required flushing of the database". Backs C2.
6. https://docs.djangoproject.com/en/stable/topics/testing/tools/ (org: Django). `TestCase` "does not truncate tables after a test. Instead, it encloses the test code in a database transaction that is rolled back at the end of the test." `setUpTestData()` is class-level data created "once for the whole `TestCase`", and "This technique allows for faster tests as compared to using `setUp()`" (with the caveat that on a database without transaction support it "will be called before each test, negating the speed benefits"). Backs C2.
7. https://www.orfium.com/engineering/speeding-up-your-python-django-test-suite/ (org: Orfium). `--keepdb` "will not destroy and recreate the database locally on every run. This gives a huge speedup when running tests locally"; measured one test at 50.299s without it versus 6.899s with it. `--parallel 6` cut "Ran 591 tests in 670.560s" to "Ran 591 tests in 305.394s". In CI, tests went from 20 minutes to 13, and the build from about 25 minutes to under 10 after switching the base class from `TransactionTestCase` to `TestCase`; on `setUpTestData` they say it "runs once for every function in the same class" and "is definitely faster" but warn "Use with caution." Backs C2.

## C3. pytest-socket / block the network; pyfakefs instead of real disk

8. https://github.com/miketheman/pytest-socket (org: pytest-socket project). The plugin exists to "disable or restrict `socket` calls during tests to ensure network calls are prevented"; it "Disables all network calls flowing through Python's `socket` interface, including DNS resolution", via `pytest --disable-socket` or `addopts = --disable-socket`, with a `socket_enabled` fixture or marker for exceptions. It states the isolation practice, not a speed claim. Backs C3.
9. https://pytest-pyfakefs.readthedocs.io/en/latest/intro.html (org: pyfakefs project, now under pytest-dev). "Using pyfakefs, your tests operate on a fake file system in memory without touching the real disk." Its alternatives section says real temporary files are "slower because the actual disk is used", while a RAM disk is "memory-based and therefore fast". Backs C3.
10. https://blog.trailofbits.com/2025/05/01/making-pypis-test-suite-81-faster/ (org: Trail of Bits). Their committed config runs `pytest` with `"--disable-socket", "--allow-hosts=localhost,::1,notdatadog,stripe"`, i.e. the suite is network-blocked except for named local/third-party hosts. This is a team describing what it does, but the post gives no speed figure for socket blocking. Backs C3.

## C4. Slow imports (`-X importtime`, local imports); test collection (`--collect-only`, `testpaths`)

11. https://blog.trailofbits.com/2025/05/01/making-pypis-test-suite-81-faster/ (org: Trail of Bits). Collection was measured with `pytest --collect-only`: "this discovery process alone consumed over 6 seconds—10% of our total test execution time after parallelization." Adding `testpaths = ["tests/"]` took "3,900+ tests collected in 7.84s" to "3,900+ tests collected in 2.60s", "a 66% reduction in collection time". For imports they "turned to profiling import times using Python's `-X importtime` option", found `ddtrace` was loaded in tests, and removing it cut `pytest --help` from 4.975s to 3.787s and total test time from 29s to 28s. Their advice list says "Speed up test discovery: Use `testpaths` in your `pytest` configuration to focus test collection on only relevant directories" and "Eliminate unnecessary imports: use `python -X importtime` to identify slow-loading modules and remove them where possible." Backs C4.
12. https://medium.com/alan/how-we-improved-our-python-backend-start-up-time-2c33cd4873c8 (org: Alan). They profiled with "`python -X importtime`" plus tuna, then moved code out of `__init__.py` files and switched costly modules to imports inside functions ("Relative imports are only loaded when the function is called"), because those imports were "awful for startup time". Results: application start-up "from 9 seconds to 6 seconds", `flask test` "from 13 seconds to 11 seconds", and unittest test start-up "from 9 seconds to 6" (20-30%). Backs C4. Note: the post's rule that absolute imports are loaded every time is their shorthand; Python caches modules in `sys.modules`.

## C5. Selective runs and guardrails: testmon / incremental / `--lf` `--ff`; slow marker; split; timeout

13. https://testmon.org/ (org: pytest-testmon project). "pytest-testmon is a pytest plugin which selects and executes only tests you need to run. It does this by collecting dependencies between tests and all executed code (internally using Coverage.py) and comparing the dependencies against changes." "Testmon always re-executes tests which failed last time", and the first run must build the dependency database with `--testmon`. Backs C5 (affected-test selection).
14. https://pytest-incremental.readthedocs.io/ (org: pytest-incremental project). The plugin "analyses your project structure and file modifications between test-runs to modify the order tests are executed and de-select tests. This allows a much faster feedback for interactive test execution." Enabled with `--inc`. Backs C5.
15. https://github.com/jerry-git/pytest-split (org: pytest-split project). It "splits the test suite to equally sized 'sub suites' based on test execution time", storing durations with `--store-durations` and running `pytest --splits 3 --group 1`. Motivation: "Splitting the test suite is a prerequisite for parallelization (who does not want faster CI builds?)." Backs C5 (CI sharding).
16. https://github.com/pytest-dev/pytest-timeout (org: pytest-timeout project). A caveat rather than a speed win: "This plugin is designed to catch excessively long test durations like deadlocked or hanging tests, it is not designed for precise timings or performance regressions. Remember your test suite should aim to be fast, with timeouts being a last resort, not an expected failure mode." Backs C5 only as "cap hanging tests; do not count it as a speed fix".
17. https://www.yeti.co/blog/using-pytest-to-write-beautiful-tests-and-a-bulletproof-django-app (org: Yeti; conference talk transcript). Marks let you separate slow tests: "Say this is an integration test, this is a slow running test - you can mark all your tests explicitly so that you can then run them differently for different reasons", and their smoke tests do not run by default. Also a caveat on xdist: with few tests "it actually ran slower because I have so few tests that the overhead of spinning up processes". Backs C5 (slow marker) and C1 (xdist overhead caveat). This is a talk transcript, weaker than a written practice post.

## C6. SQLAlchemy: joining a Session into an external transaction

18. https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#joining-a-session-into-an-external-transaction-such-as-for-test-suites (org: SQLAlchemy). Section "Joining a Session into an External Transaction (such as for test suites)". The docs say the recipe binds the Session to a `Connection` already in a transaction and that "the `Session.join_transaction_mode` parameter is passed with the setting `"create_savepoint"`", "which indicates that new SAVEPOINTs should be created in order to implement BEGIN/COMMIT/ROLLBACK for the `Session`, which will leave the external transaction in the same state in which it was passed." Their example is:

```python
self.connection = engine.connect()
self.trans = self.connection.begin()
self.session = Session(
    bind=self.connection, join_transaction_mode="create_savepoint"
)
...
self.session.close()
self.trans.rollback()
self.connection.close()
```

The PASS example in the task is the same recipe with local names (`conn`, `tx`, `session`): parameter names `bind` and `join_transaction_mode`, value exactly `"create_savepoint"`, then `Session.close()`, `Transaction.rollback()`, `Connection.close()`. It matches. Note the docs' `Session` is a `sessionmaker()` instance, and SQLAlchemy says the recipe "is part of SQLAlchemy's own CI to ensure that it remains working as expected". Backs C6.

## Counts

- C1 (xdist session fixtures / one DB per worker): 4 organisations/projects — pytest-xdist, pytest-django, Trail of Bits, EXANTE. High confidence. Two of the four are pytest-plugin projects (pytest-xdist and pytest-django both sit in the pytest-dev orbit), so the independent-company evidence is Trail of Bits and EXANTE.
- C2 (`--reuse-db`, `--create-db`, TestCase rollback, `setUpTestData`): 3 — pytest-django, Django, Orfium. High confidence. Orfium is the only independent company, and it demonstrates Django's `--keepdb`/`--parallel`, not pytest-django's `--reuse-db`; the pytest-django flags rest on the project's own docs.
- C3 (block the network; fake filesystem): 3 — pytest-socket, pyfakefs, Trail of Bits. Medium confidence: pytest-socket and Trail of Bits state the isolation practice without a speed number; only pyfakefs explicitly contrasts in-memory with "slower because the actual disk is used".
- C4 (`-X importtime` / local imports; `--collect-only` / `testpaths`): 2 — Trail of Bits, Alan. High confidence on `-X importtime`, `testpaths`, and `--collect-only`; the Alan post is a company engineering post with measured start-up numbers. `norecursedirs` has no independent source here (its documentation lives on docs.pytest.org, which the brief excludes).
- C5 (testmon/incremental; `--lf`/`--ff`; slow marker; split; timeout): 5 — pytest-testmon, pytest-incremental, pytest-split, pytest-timeout, Yeti. Medium confidence. `--lf`/`--ff` has no new independent source: the primary documentation is docs.pytest.org, already used, and the only alternatives found were vendor listicles. pytest-timeout is a caveat, not a speed practice. Yeti is a transcript.
- C6 (SQLAlchemy join_transaction_mode): 1 — SQLAlchemy. High confidence for the exact parameter names and the recipe (primary documentation, and the page says the recipe runs in SQLAlchemy's CI); low independent corroboration, since only the project documents it.

Overall: C1, C2, C4, and C6 are well supported by primary docs plus at least one independent company post (C6 excepted, docs only). C3 and C5 are supported as practices but with thinner independent evidence and, for C5, one sub-item (`--lf`/`--ff`) that rests on the already-used pytest docs.
