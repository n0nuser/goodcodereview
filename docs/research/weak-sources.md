# Weak-source pass: English identifiers, subtype substitution, bounded background tasks

Fetched 2026-10-24. Pages read through WebFetch (a small model summarises the page) unless marked "raw": raw means the text was read directly (curl plus pdftotext). Everything below is paraphrase. Each row gives the URL, what it says, strength, and the card id it supports. "Partial" marks pages where the fetch tool truncated the text or I read only the relevant part.

## 1. fn-english-identifiers

1. https://peps.python.org/pep-0008/. Section "Source File Encoding": identifiers in the standard library must be ASCII-only and should use English words where feasible; abbreviations and technical terms may be non-English; projects with a global audience are encouraged to adopt the same policy. Section "Comments": coders outside English-speaking countries should write comments in English, unless they are very sure the code will never be read by people who do not speak their language. Section "Naming Conventions > ASCII Compatibility" points to PEP 3131. Strength: primary (the language's own style guide), but scoped to the stdlib plus advice. Supports `fn-english-identifiers`. Note: the "unless 120% sure" exception is the project-policy escape hatch the card already uses.
2. https://peps.python.org/pep-3131/ (Policy Specification, Rationale, Common Objections, Discussion). Stdlib identifiers, string literals and comments must be ASCII; English preferred for names. This is also the credible counter-view, from the same authors: developers not fluent in English can name things in their own language, which they argue helps clarity for speakers of that language; the library author, not the language, decides the policy; projects wanting wide reuse may still pick English-only. Strength: primary, and balanced. Supports `fn-english-identifiers` (rule and counterpoint).
3. https://llvm.org/docs/CodingStandards.html (section "Commenting", partial: last 1k characters unread). Comments are to be written as English prose with proper capitalisation and punctuation; diagnostics use correct English prose. Does not forbid non-English identifiers explicitly. Strength: primary (project's own standard), comments only. Supports `fn-english-identifiers`.
4. https://devguide.python.org/documentation/style-guide/. CPython docs prose: the audience is worldwide and may not be native English speakers, so write plain English. Says nothing about code comments or identifiers. Strength: primary but only tangential (prose docs, not code). Supports `fn-english-identifiers` weakly (same reasoning: readers outside one language group).
5. https://www.kernel.org/doc/html/latest/process/coding-style.html. Checked: no rule on the language of comments or identifiers; only asks for correct spelling in kernel messages. Negative finding, not a source. 
6. https://go.dev/doc/effective_go (partial) and https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/coding-style/identifier-names. Neither states a language rule. Effective Go has none that I found; the C# page says identifiers may hold any Unicode letters, and asks for meaningful, descriptive names. Negative findings: the languages allow non-English identifiers and leave policy to the project. Supports the "project-policy check" framing of `fn-english-identifiers`.
7. https://google.github.io/styleguide/pyguide.html (partial). Examples use English throughout, but no rule states it. Negative finding.

Not found: any ISO or standards-body rule, any Rust or Java official statement, a Mozilla or Google rule that names English for code.

Verdict: still weak as a universal rule, but now honest and well-sourced as a conditional rule. PEP 8 (items 1) and PEP 3131 (item 2) together give the rule, the exception and the counter-view from one primary owner; LLVM (item 3) adds a second large project for comments. Keep `severity: discuss` and the note "project policy". Recommended borrowed_from: https://peps.python.org/pep-0008/, https://peps.python.org/pep-3131/, https://llvm.org/docs/CodingStandards.html. Update the card note: the stdlib scope still holds, but PEP 8 also gives general advice for comments.

## 2. mod-subtype-passes-parent-tests

8. https://www.cs.columbia.edu/~wing/publications/LiskovWing94.pdf (Liskov and Wing, TOPLAS 16(6), Nov 1994). Read raw: the CMU URL used earlier gave an image-only file (a different scan); this Columbia copy has a text layer (OCR-quality, 15k words). I read the abstract and the Figure 4 definition of the subtype relation, not the whole paper. Abstract: the subtype relation should ensure any property proved about supertype objects also holds for subtype objects. Definition (Section 4, Fig. 4): subtype methods preserve supertype method behaviour through (a) an invariant rule, the subtype's invariant implies the supertype's under the abstraction function; (b) signature rules, argument types contravariant, result covariant, no new exceptions; (c) a methods rule, the supertype precondition implies the subtype precondition (weaker or equal) and the subtype postcondition implies the supertype postcondition (stronger or equal); (d) a constraint rule for history properties, so a subtype cannot allow state changes the supertype forbids. Strength: primary (original authors). Supports `mod-subtype-passes-parent-tests`. Caveat: the paper is about specifications and proofs, not test suites; "run the parent's tests against the subclass" is an engineering proxy for it, so say "proxy" in the card.
9. https://dspace.mit.edu/handle/1721.1/149735. Record page for the earlier MIT report MIT-LCS-TR-562b, "Family Values" (Aug 1993), same authors; the PDF is on the page. Not read. Strength: primary, earlier version; alternative if the Columbia link dies. Supports `mod-subtype-passes-parent-tests`.
10. Liskov, "Data Abstraction and Hierarchy", OOPSLA 1987 keynote, SIGPLAN Notices 23(5), 1988, pp. 17-34, DOI 10.1145/62139.62141. Only the citation was confirmed, through a search result; the text was not found free and not read. Strength: primary but unread; cite only as background, do not put in `borrowed_from` as a read source.
11. https://www.eiffel.org/doc/solutions/Design_by_Contract_and_Assertions (section "Contracts and Inheritance"; partial but the section was read). In Eiffel, descendants inherit preconditions, postconditions and invariants; a redefined routine may only weaken the precondition (the `require else` form ORs alternatives) and only strengthen the postcondition (`ensure then` ANDs extras); new invariants are ANDed with inherited ones. The stated reason: dynamic binding stays safe, a descendant cannot demand more of clients but may promise more. Strength: primary (Eiffel Software, Meyer's language, first-party docs). Supports `mod-subtype-passes-parent-tests`. It is the same rule as item 8 methods rule, in a language that enforces it at run time.
12. https://mypy.readthedocs.io/en/stable/common_issues.html (section "Incompatible overrides"). mypy reports an override that narrows an argument type, adds a required parameter or drops an optional one, and names the Liskov substitution principle as the reason. Strength: primary for the tool, and the only language-level doc found that cites Liskov by name. Covers the signature half only, not behaviour. Supports `mod-subtype-passes-parent-tests` (tool gate for the signature part).
13. https://typing.python.org/en/latest/spec/glossary.html. Defines subtype as a value-set subset, and "assignable"; never mentions Liskov or behaviour. https://docs.python.org/3/library/typing.html and https://peps.python.org/pep-0484/ discuss variance for generics only, nothing on overrides. Negative finding: Python's typing spec does not own the Liskov rule; do not cite it for it.

Verdict: now strong on the rule, with one honest gap. Items 8 and 11 are the two primary sources (Liskov and Wing for the formal rule; Meyer's Eiffel docs for the pre/post form), item 12 gives a tool for the signature half. The card's own claim "passes the parent's tests" is an engineering proxy, so the card should say that. Recommended borrowed_from: https://www.cs.columbia.edu/~wing/publications/LiskovWing94.pdf, https://www.eiffel.org/doc/solutions/Design_by_Contract_and_Assertions, https://mypy.readthedocs.io/en/stable/common_issues.html. Keep Hillel Wayne as secondary context only. Change the card note: the paper was read (abstract and definition, not all sections).

## 3. Bounding background tasks (unbounded concurrent spawning)

14. https://docs.python.org/3/library/asyncio-task.html (anchors `#creating-tasks`, `#task-groups`). create_task: keep a reference to the result, because the loop holds tasks only weakly and a task can vanish mid-run. TaskGroup keeps strong references, awaits every task on exit, cancels the rest when one fails, and raises the failures as an ExceptionGroup. The page states no concurrency cap; TaskGroup and gather start everything at once. Strength: primary. Supports a new card (lifetime half) and `fn-resource-lifetime`.
15. https://docs.python.org/3/library/asyncio-sync.html. Semaphore holds a counter of permits; acquire blocks at zero; the example comments "at most 10 tasks use the resource at once"; BoundedSemaphore raises if released too often. Strength: primary. Supports a new card (the cap half). Note: the docs do not link Semaphore to task spawning, so the pairing is inference.
16. https://vorpus.org/blog/notes-on-structured-concurrency-or-go-statement-considered-harmful/ (Nathaniel Smith). A spawned task with no scope loses its errors and outlives its caller; a nursery block that does not exit until all children finish fixes both. The article does not discuss resource limits or caps. Strength: primary (original author of the idea; already cited for `fn-resource-lifetime`). Supports lifetime half only; do not cite it for bounding.
17. https://pkg.go.dev/golang.org/x/sync/errgroup. A zero Group has no limit; SetLimit(n) caps active goroutines and Go blocks until a slot is free; TryGo starts one only if a slot is free and reports it; the first error cancels the group context. Strength: primary (Go team package docs). Supports the new card: a cap, with block or reject on full.
18. https://go.dev/blog/pipelines (section "Bounded parallelism" and cancellation sections). One goroutine per input can use more memory than the machine has; the fix is a fixed number of workers reading a shared channel. Also: a stage that stops reading leaves senders blocked forever, so every stage needs a cancellation signal. Strength: primary (Go blog, Sameer Ajmani). Supports the new card and `svc-stream-dont-materialise`.
19. https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html. Semaphore caps how much runs at once (files, requests, connections); the doc's example spawns 20 tasks that wait on 4 permits. Strength: primary. Supports the new card (also shows that spawning is still unbounded while execution is capped, so memory per waiting task remains).
20. https://tokio.rs/tokio/tutorial/channels. Queues must be bounded or they fill memory; a full channel makes `send().await` wait, which is backpressure; concurrency should be introduced explicitly and total concurrency capped (accept loop should limit sockets); the right capacity depends on the application. Strength: primary. Supports the new card and `sys-load-shedding-bounded-queues`.
21. https://docs.rs/tokio/latest/tokio/task/struct.JoinSet.html. JoinSet is the owning collection for spawned tasks; dropping it aborts them. No bounding feature. Strength: primary. Supports the lifetime half only.
22. https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload (the Amazon Builders' Library article, moved from aws.amazon.com/builders-library). Services should do bounded work per request (pagination); bound queue size and wait time and drop stale items; connection limits are blunt; rejecting excess early protects goodput; unbounded work under load raises latency past client timeouts, wasting work and triggering retries. Strength: primary (the operator's own engineering write-up). Supports `sys-load-shedding-bounded-queues`; request-serving, not task-spawning.
23. https://sre.google/sre-book/handling-overload/. Per-client quotas, per-task rejection thresholds, criticality-based shedding, retry budgets. States nothing on bounded queues or per-request hard caps (checked). Strength: primary but off-target; use only for shedding in `sys-load-shedding-bounded-queues`.

Verdict: enough primary material for its own card, and it is not the same as `sys-load-shedding-bounded-queues`, which is about a service refusing requests. The new rule is local to one program: a loop that spawns a task per item (per request, message, file) needs a cap on in-flight tasks and a scope that owns them. Suggested id `svc-bounded-background-tasks` (level service or function; tool_gate: grep for create_task, `go func`, `tokio::spawn` or `Promise.all(items.map(...))` inside a loop without a semaphore, limit or pool). Rule in one line: cap the number of in-flight tasks started from an unbounded input, and keep every task owned by a scope. Recommended borrowed_from: https://pkg.go.dev/golang.org/x/sync/errgroup, https://go.dev/blog/pipelines, https://docs.python.org/3/library/asyncio-sync.html, https://docs.python.org/3/library/asyncio-task.html, https://tokio.rs/tokio/tutorial/channels. Keep the Nathaniel Smith article on `fn-resource-lifetime`, not here. A caution for the card writer: a semaphore inside a spawned task (item 19) still creates all the tasks; the real cap is where the task is created (errgroup SetLimit, a worker pool, or acquire before spawn). That caveat is not stated as such in the docs; it follows from items 17-19.
